## 0. Цель

Развести три принципиально разных сценария, которые сейчас перемешаны в
одном экране и в одном коде:

| Сценарий | Семантика | Влияние на базу |
|---|---|---|
| **Export** | read-only выгрузка | **никакого** |
| **Import (CSV)** | merge — добавление внешних данных | добавляет, не удаляет |
| **Restore (.afb)** | replace — полная замена базы | заменяет всё |

Приоритеты (в этом порядке): **целостность финансовых данных → отсутствие
дубликатов → обратная совместимость → понятный UX → визуальная полировка.**

### 1.2 Экспорт

- `AF.Services.Export.csv(txList, state)` — 12 колонок формата Money Flow:
  `Дата, Счёт, Сумма, Валюта, Категория, Контрагент, Перевод: Счёт,
  Перевод: Сумма, Перевод: Валюта, Метки, Место, Примечание`.
  Порядок и содержимое зафиксированы `tests/export_service.test.js`
  (**контракт менять нельзя** — round-trip экспорт→импорт на нём держится).
  Иерархия пишется одной колонкой «Категория / Подкатегория».
- `AF.Services.Export.xlsHtml()` — **не XLSX**, а HTML-таблица с расширением
  `.xls`. Excel/Numbers открывают её через legacy-импортёр и показывают
  предупреждение о несовпадении формата.
- `AF.Services.Export.reportHTML()` — HTML-отчёт, печатается через
  `window.open` + `print()` (PDF делает сама ОС).
- Период: `exportRange()` — только `month` / `year` / `all`, рассчитывается
  инлайн, без `AF.Services.Period`; фильтр `exportTx()` — `new Date(t.date)`
  (полуночный UTC-разбор `'YYYY-MM-DD'`, см. H-5 в `TASK_025`).

**Вывод:** экспорт действительно read-only и данные не меняет
(`doBackupCreate` — исключение, он пишет `state.lastBackup`). Не хватает
периодов и настоящего `.xlsx`.

### 1.3 Импорт CSV

`importCSV(text)` (`index.html:5919-6011`) — одна функция ~90 строк, которая
одновременно парсит, сопоставляет колонки, **создаёт счета и категории** и
пишет в базу. Проблемы:

1. **Нет анализа файла.** Пользователь не видит, что распознано, пока не
   нажмёт «ОК» в `confirm()`.
2. **Нет detection дубликатов.** Повторная загрузка того же файла создаёт
   полный дубль всех операций. Это главный дефект.
3. **Нет column mapping UI.** `find()`/`findMain()` угадывают колонки по
   подстрокам; если не угадали — `toast('Не нашёл колонки даты/суммы.
   Пришли файл — настрою.')` и тупик.
4. **Побочные эффекты во время разбора.** `ensureAcc()`/`ensureCat()`/
   `resolveCatPath()` пушат в `state.accounts`/`state.cats`/`state.subcats`
   прямо в цикле парсинга — до какого-либо подтверждения. Откат держится
   только на `AF.Store.rollback()` из `TASK_026`.
5. **Нет mapping счетов/категорий.** Сопоставление — точное совпадение имени
   в нижнем регистре. `Groceries` при существующей `Продукты` создаёт новую
   категорию; `ING ` с пробелом совпадёт, `ing bank` — нет.
6. **`confirm()`** вместо UI приложения (§18 постановки прямо запрещает).
7. **Кодировка не определяется** — `FileReader.readAsText(f)` без аргумента,
   то есть всегда UTF-8. Экспорт Money Flow в cp1251 придёт «кракозябрами»,
   и это молча превратится в имена категорий.
8. Разделитель определяется по **первой непустой строке** — если в заголовке
   есть запятые внутри кавычек, выбор может быть неверным.
9. Переводы: логика ветвления `from`/`to` по знаку суммы в целом верна и
   двойного учёта не даёт (`type:'transfer'` — одна запись с `from`/`to`/
   `amount`/`toAmount`), но `toAmount` в мультивалютном переводе не
   валидируется, а строки без распознанного счёта молча уходят в
   `state.accounts[0]`.

### 1.4 Импорт JSON и `.afb`

- `importJSON(d)` — merge/replace состояния целиком из JSON (после
  `TASK_026` — с записью до подмены состояния).
- `AF.Services.Backup.create(state)` — конверт
  `{app:'Alex Finance', schemaVersion, createdAt, data:state}`.
  Так как `data` — **весь** `state`, копия фактически уже полная:
  `tx, accounts, accountGroups, budgets, cats, subcats, goals, reminders,
  healthHistory, settings, currency, theme, rates, hideAmounts, pinHash,
  lastBackup, groupCollapsed, profileName, avatar, taxonomyVersion,
  schemaVersion, updatedAt` (проверено перечислением всех обращений
  `state.*` в `index.html`). Отдельных сущностей вне `state` нет.
- `AF.Services.Backup.restore(text)` — `JSON.parse` + единственная проверка
  `Array.isArray(data.tx)`. **Нет** checksum, `appVersion`, формата-
  идентификатора, проверки «копия новее приложения», превью и safety-копии.
- `doBackupRestore()` (`index.html:3900`) — `confirm()`, затем
  `AF.Store.save(next)` и только при успехе подмена состояния (`TASK_026`).
  Прежняя база при отказе записи цела, но **валидации результата после
  записи нет**, а safety-копия не создаётся.

### 1.5 Storage / persistence / схема

- `AF.Store` (`js/database/store.js`) — репозиторий поверх `localStorage`,
  один ключ `finance_app`, `SCHEMA_VERSION = 3`, идемпотентный `migrate()`.
- `AF.Store.save()` возвращает `AF.Result` с кодами `QUOTA_EXCEEDED` /
  `SERIALIZATION_FAILED` / `STORAGE_FAILED`; есть `snapshot()` (последний
  успешно сохранённый JSON), `markSaved()` и `rollback(state)`, который
  восстанавливает данные **внутрь того же объекта** `state`.
  Это готовый примитив транзакции — §12 и §17 строятся на нём, второй
  механизм не заводится.
- Обёртка `save()` в `index.html:2769` — откат + `toastError` + перерисовка.
  Контракт `if(!save().ok)return;` защищён сканером в
  `tests/reliable_save_screen.test.js` §2.

## 3. Целевая архитектура

Существующий слой сервисов сохраняется, naming — как в проекте
(`js/services/*_service.js`, `AF.Services.X`, чистые функции без DOM и
`localStorage`, комментарий-шапка с указанием Flutter-аналога).

```
Export
  export_service.js        (есть)  CSV + HTML-отчёт + данные для XLSX
  xlsx_writer_service.js   (нов.)  минимальный писатель OOXML .xlsx (ZIP)

Import
  csv_parser_service.js    (нов.)  кодировка, разделитель, кавычки, строки
  import_source_service.js (нов.)  определение источника + auto column mapping
  import_mapping_service.js(нов.)  нормализованный подбор счетов и категорий
  import_service.js        (нов.)  план импорта, дубликаты, валидация, apply

Backup
  backup_service.js        (расш.) create / inspect / migrate / restore
```

Разделение ответственности: **ни один** сервис не пишет в хранилище.
`import_service.apply()` возвращает **новое** состояние; запись — только
`AF.Store.save()` из UI.

## 4. Требования

### 4.1 Экран

Разделы: **Экспорт** (период + PDF / Excel `.xlsx` / CSV) → **Импорт
данных** (📥 Импортировать CSV) → **Резервные копии** (создать / восстановить).
Период: текущий месяц, прошлый месяц, текущий год, прошлый год, вся история,
свой период (две даты).

### 4.2 CSV Import Flow

1. Выбор файла → чтение как `ArrayBuffer`, определение кодировки (UTF-8 с
   fallback на windows-1251), BOM, разделителя, кавычек. **База не меняется.**
2. Экран анализа: найдено операций, период, валюты, счета, категории,
   предполагаемый источник (`Money Flow` / `A-Lex Finance` / `CSV`).
3. Column mapping: уверенные колонки подставлены автоматически, остальные —
   выбор пользователя. Обязательны дата и сумма.
4. Mapping счетов и категорий: нормализованное сравнение, «использовать
   существующий» / «создать новый», авто-подбор при уверенном совпадении
   (включая двуязычные синонимы вида `Groceries` → `Продукты`).
5. Дубликаты: устойчивый fingerprint (дата + тип + сумма + валюта + счёт +
   категория + контрагент/примечание + счёт-получатель для перевода).
   По умолчанию — пропускать.
6. Превью: сколько будет добавлено, новых счетов, новых категорий,
   пропущенных дубликатов, проблемных строк. **До нажатия кнопки база не
   меняется.**
7. Атомарная запись: клон состояния → применение плана → валидация → запись
   → при ошибке состояние в памяти не тронуто.
8. Результат: добавлено / создано / пропущено / ошибочных строк +
   «Отменить импорт».

### 4.3 Backup

- Конверт: `format`, `backupVersion`, `schemaVersion`, `appVersion`,
  `createdAt`, `counts`, `checksum` (канонический FNV-1a по payload), `data`.
- Ключ `app` оставлен для совместимости со старыми читателями.
- `inspect()` различает: валидная копия v2, легаси-копия (`{app,data}`),
  «голый» state, битый JSON, чужой JSON, копия новее приложения,
  несовпадение checksum, слишком большой файл.
- Restore: превью (дата, операции, счета, категории, версия схемы,
  предупреждение о замене) → авто-создание safety-копии текущей базы →
  запись → валидация записанного → при любой ошибке возврат прежнего
  состояния.

### 4.4 Ошибки

Без `alert()` и без `confirm()` на путях импорта/восстановления. Обрабатываются:
невалидный JSON/AFB, пустой CSV, отсутствие обязательных колонок, неизвестная
кодировка, NaN-суммы, неразбираемые даты, неизвестные валюты, битая схема,
копия из новой версии, слишком большой файл, отказ записи в хранилище.

### 4.5 UX

Мобильный viewport без горизонтального выхода; таблицы mapping — карточки со
своим скроллом; tap target ≥ 44px; восстановление визуально отличается от
импорта (destructive-стиль); прогресс и блокировка повторных нажатий на
длинных операциях; светлая и тёмная темы.

## 5. Критерии готовности

1. Export — ни один экспорт не меняет `localStorage`.
2. Import CSV — анализ → mapping → дубликаты → превью → атомарный merge →
   результат.
3. Restore AFB — валидация → safety-копия → атомарная замена → откат при
   любой ошибке.
4. Повторный импорт того же файла не создаёт ни одной новой операции.
5. Старые `.afb` восстанавливаются.
6. Перевод не превращается в двойной доход/расход.
7. Полный набор тестов зелёный.
8. Проверка в браузере по сценариям A–J.

## 6. План проверок

**Тесты:** экспорт (3 формата не меняют storage, период применяется),
CSV-парсер (`,` / `;` / кавычки с запятыми / UTF-8 / BOM / cp1251 / русские
заголовки Money Flow / пустые строки), mapping (существующий счёт
переиспользуется, новый создаётся, категории, неизвестная колонка),
дубликаты (повтор не дублирует; похожие, но разные — не теряются),
безопасность импорта (ошибка разбора / валидации / записи → 0 изменений),
restore (валидный / битый / старая схема / новая несовместимая схема / отказ
записи / успех), переводы (нет двойного учёта).

**Браузер:** сценарии A–J из постановки + console errors + мобильный
viewport + светлая/тёмная тема + отсутствие регрессий в обычном CRUD.

## 7. Фактический результат

### 7.1 Что реализовано

**Новые сервисы** (чистые функции, без DOM и без `localStorage`):

| Файл | Ответственность |
|---|---|
| `js/services/csv_parser_service.js` | кодировка (UTF-8 → windows-1251 → UTF-16), BOM, выбор разделителя полным разбором, кавычки по RFC 4180, пустые строки |
| `js/services/import_source_service.js` | определение источника + автоматическое сопоставление колонок (ru/en/es/de), transfer-колонки разбираются раньше основных |

| `js/services/import_service.js` | разбор строк в операции, детектор дубликатов, валидация, `apply()` в новое состояние, `undo()` |
| `js/services/xlsx_writer_service.js` | настоящий `.xlsx`: ZIP (store + CRC32) и OOXML, даты датами, суммы числами |

`.xls` на настоящий `.xlsx`. Восстановление отличается от импорта красной
рамкой и красным заголовком строки.

**Мастер импорта** — 4 шага: анализ файла → сопоставление (колонки, счета,
категории) → предпросмотр → результат. `confirm()` на этом пути больше нет.
Проверено конструктивно (тест §B4): ни один шаг, кроме `impCommit()`, не
обращается ни к `AF.Store.save()`, ни к `state.*.push`.

**Атомарность импорта.** `Import.apply()` клонирует состояние, применяет план
к клону и возвращает новое состояние; исходный `state` не меняется ни на байт.
Запись — единственный вызов `AF.Store.save(applied.value)`; при отказе
результат просто выбрасывается, и в памяти остаётся прежняя база.

**Восстановление.** `inspect()` → предпросмотр → safety-копия файлом →
`migrateBackup()` → запись → **перечитывание из хранилища** → сверка
счётчиков → и только потом «Данные восстановлены ✓». При несошедшейся сверке
прежняя база возвращается из `AF.Store.snapshot()`.

**Отмена импорта** реализована через `importBatchId` на созданных сущностях +
журнал `state.importBatches`. Счёт или категория, на которые успела сослаться
собственная операция пользователя, при отмене сохраняются.

### 7.4 Известные ограничения

- «Отменить импорт» доступна на экране результата сразу после импорта.
  Журнал `importBatches` сохраняется, но отдельного экрана истории импортов
  нет — это отдельная задача.
- Дубликаты ищутся только по операциям; повторный импорт не «чинит» уже
  созданные ранее дубли — он лишь не создаёт новых.
- Кодировки: UTF-8, windows-1251, UTF-16. Другие однобайтовые кириллические
  кодировки (KOI8-R, CP866) не распознаются и дадут ошибку, а не «кракозябры».
- `.xlsx` пишется методом store (без сжатия) — файл больше, чем у Excel,
  но формат полностью корректен.
- Автоматическая safety-копия перед restore отдаётся файлом в загрузки; в
  хранилище второй экземпляр базы не пишется (это удвоило бы расход квоты —
  см. `TASK_037`).
