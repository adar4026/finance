## Почему TASK_003A, а не TASK_004

Это исправление первопричины и точечная доработка визуального стиля уже
существующего компонента Главной (переключатель День/Неделя/Месяц/Год/Период
+ финансовая карточка из `TASK_003`), а не новая продуктовая функция.

этап и не должен быть занят корректирующей задачей — поэтому использован
суффикс `A` у уже закрытой `TASK_003`, к которой относится это исправление.

## Цель

1. Устранить первопричину: переключение вкладок «День/Неделя/Месяц/Год/
   Период» на Главной не пересчитывало новую финансовую карточку
   (`TASK_003`), потому что у карточки было отдельное, не связанное с общим
   `period`/`anchor` состояние `cardMonth`.
2. Заменить яркую сиреневую заливку активной вкладки переключателя на
   спокойный стеклянный индикатор в стиле нижнего tab bar (`TASK_002`).

## Найденная первопричина

`js/services/finance_card_service.js` и рендер карточки в `index.html`
(`renderFinanceCard()`) были построены вокруг собственной переменной
`cardMonth` (задокументированное архитектурное решение `TASK_003`,
раздел «карточка не переиспользует общий `.subhead`»). Общий переключатель
`#periods` (День/Неделя/Месяц/Год/Период) продолжал управлять только
глобальным `period`/`anchor`, которые использовались для списка операций
(`#recentList`), Аналитики и Бюджетов — но **не** передавались в карточку.
Визуально вкладки переключались (`.on` класс, `render()` вызывался), но
`renderFinanceCard()` каждый раз пересчитывал ровно то же самое —
календарный месяц из `cardMonth`, а не выбранный пользователем диапазон.
Двух параллельных, конкурирующих состояний периода не было — было одно
глобальное (`period`/`anchor`) и одно полностью изолированное (`cardMonth`),
не подключённое к переключателю вообще.

## Единый источник периода (решение)

- `cardMonth` **удалён**. Карточка теперь всегда использует общий `period` +
  `anchor` (те же, что управляют списком операций, Аналитикой и Бюджетами).
- Новый модуль `js/services/period_service.js` (`AF.Services.Period`) —
  чистые функции диапазона/подписи/сдвига/проверки будущего, извлечённые из
  ранее инлайновых `periodRange()`/`periodLabel()`/`shiftPeriod()`
  (перенесены как есть — поведение Аналитики и Бюджетов не изменилось,
  устранено только дублирование расчёта дат). `index.html` теперь делегирует
  в `AF.Services.Period`, а не пересчитывает диапазон самостоятельно.
- `renderFinanceCard()` вызывает `periodRange()` (общую, теперь
  делегирующую в сервис) и передаёт вычисленные `{from,to}` в
  `AF.Services.FinanceCard` — сервис карточки больше не знает о «месяце»,
  только о диапазоне.
- Стрелки над карточкой (`#fcMonthPrev`/`#fcMonthNext`, `.month-switch`)
  вызывают ту же общую `shiftPeriod()`, что и стрелки `#prevP`/`#nextP`
  общего `navrow` на Аналитике/Бюджетах — единая точка сдвига `anchor`.
  Подпись над карточкой — общая `periodLabel()` (капитализированная
  `fcCapFirst()` только для отображения, сама функция не меняется).
- Циклических обновлений/двойного рендера нет: `shiftPeriod()`/переключение
  вкладки `#periods` вызывают ровно один `render()`, который синхронно
  обновляет `#recentList`, карточку, Аналитику, Бюджеты, Счета, шапку.

## Правила пяти диапазонов (`AF.Services.Period.range`)

Все границы — в локальном времени (не UTC), проверено тестами на операциях
у полуночи.

- **День** — выбранный локальный календарный день, `00:00` → `23:59:59.999`.
- **Неделя** — понедельник `00:00` → воскресенье `23:59:59.999` (проект не
  имел отдельного правила начала недели до этой задачи — принято
  понедельник, как в постановке).
- **Месяц** — 1 число `00:00` → последний день месяца `23:59:59.999`
  (поведение `TASK_003` сохранено без изменений).
- **Год** — 1 января `00:00` → 31 декабря `23:59:59.999`.
- **Период** — существующий пользовательский `customFrom`/`customTo`
  (`applyRangeDates()`, не менялась); если пользователь ещё не выбирал —
  безопасный дефолт (начало текущего месяца → сейчас), как было раньше.

Капитал «на конец диапазона» везде считается как `min(to, сейчас)` —
для диапазона, содержащего текущий момент, используется фактическое
состояние на текущий момент, будущие операции не могут существовать
физически, поэтому отдельного «обрезания» списка операций по `now` не
требуется (совпадает с решением `TASK_003` для месяца, обобщено на все
режимы). Не разрешён переход в будущий диапазон стрелкой «вперёд»:
`AF.Services.Period.isFutureRange(period, кандидат-после-сдвига, now)`
дизейблит `#fcMonthNext` (`disabled` + `aria-disabled`) для День/Неделя/
Месяц/Год; вкладка «Период» стрелками не двигается (как и раньше у общего
`navrow` — сохранено существующее поведение, стрелки скрыты `visibility`,
подпись тапабельна и открывает `openRange()`).

## Пересчёт сумм, капитала и графика

`js/services/finance_card_service.js` обобщён с «месяца» на произвольный
`{from,to}`:

- `txInRange`/`totals` — доходы/расходы/поток/счётчики строго внутри
  диапазона; переводы (`type==='transfer'`) исключены моделью данных.
- `capitalAtRangeEnd`/`capitalChange` — капитал на `min(to,now)` и изменение
  относительно капитала на момент перед началом диапазона (та же формула
  `TASK_003`, обобщённая на `from`).
- **График возвращён в карточку** (в исходном `TASK_003` был убран после
  ревью по запросу пользователя как избыточный для месяца; в TASK_003A явно
  затребован постановкой заново, уже для всех пяти режимов) — накопленные
  линии доходов (зелёная сплошная) и расходов (красная пунктирная),
  переиспользован ранее существовавший визуальный приём (`fcEndMarkers`,
  кастомный `external` tooltip, шкала справа, несколько подписей по оси X)
  из версии карточки до упрощения (`git show 02f5cc9`), адаптированный под
  произвольный диапазон вместо только месяца.
- Детализация графика (`FC.granularityFor`): День → по часам (24 точки,
  простое читаемое решение по времени суток); Неделя и Месяц → по дням;
  Год → по месяцам; Период → по дням для диапазона ≤62 дней, иначе по
  месяцам (агрегация для длинных диапазонов, без сотен подписей).
  `FC.gridBuckets`/`FC.cumulativeSeries` строят бакеты и накопительные
  суммы; бакет без операций продолжает накопленное значение (не сбрасывается
  в 0), включая ещё не наступившие бакеты текущего диапазона — конечная
  точка линии всегда численно совпадает с `totals().income/expense`
  (проверено тестами и вручную).
- Пустой диапазон — `#fcEmptyMsg` («Нет операций за <режим>») поверх
  графика без сдвига высоты карточки, показатели нулевые, фиктивных линий
  нет.
- Приватный режим (`state.hideAmounts`) маскирует капитал, изменение, три
  нижних показателя, подписи-бабблы на концах линий и шкалу графика (через
  существующие `num()`/`fmtCur()`/`maskAmt()`); линии и подписи дат остаются
  видимыми. Переживает переключение вкладок и перезагрузку страницы
  (существующий персистентный `state.hideAmounts`, логика не менялась).

## Подпись диапазона и стрелки

Подпись над карточкой — общая `periodLabel()` (раздел 8 постановки уже
соответствовал её существующему формату): День — «26 июля»; Неделя —
«20 июл. – 26 июл.»; Месяц — «Июль 2026 г.»; Год — «2026»; Период — выбранные
даты («1 июл. – 26 июл. 2026 г.») или «Всё время». `aria-label` стрелок
динамический по режиму («Предыдущий день»/«Следующая неделя»/…). Хиты
кнопок — 44×44px (без изменений разметки/стилей `.month-switch .m-arrow`,
унаследовано от `TASK_003`). Дублирующей строки месяца на Главной по-прежнему
нет — общий `#navrow` остаётся скрытым для `id==='scrRecords'`, единственная
строка диапазона — `#fcMonthSwitch`, теперь управляющая общим состоянием.

## Стеклянный индикатор переключателя (раздел 11)

Активная капсула `.periods button.on` больше не залита `var(--accent)`
(ярко-сиреневый). Токены переиспользованы из нижнего tab bar (`TASK_002`,
без создания новых почти одинаковых значений): `--nav-glass-bg`,
`--nav-glass-border`, `--nav-glass-shadow` — тот же полупрозрачный
светлый/тёмный градиент, `backdrop-filter:blur(14px) saturate(160%)`,
тонкая граница, мягкая тень. Активный текст — `var(--nav-blue)` (тот же
синий акцент, что и активная подпись нижнего таб-бара) поверх стекла.
`@supports not (backdrop-filter)` — CSS fallback остаётся читаемым за счёт
градиента/границы/тени без блюра.

Реализация — новый `#periodsIndicator` (`.periods-indicator`), общий для
`.periods` (используется и на Главной, и на Аналитике — один и тот же DOM-
узел). `movePeriodsIndicator(instant)` — тот же приём, что и
`moveNavIndicator()` из `TASK_002`: позиция/ширина по фактической
`getBoundingClientRect()` активной кнопки, не по жёстким координатам —
корректно на 320/375/390/430px и после ресайза (`ResizeObserver` на
`#periods` + `resize`/`orientationchange`). Движение — `transform:
translateX()` + `width` с CSS `transition`; `@media
(prefers-reduced-motion: reduce)` отключает transition перемещения (иконки/
подписи остаются, opacity-переход для скрытия/появления сохраняется).
Индикатор скрывается (`opacity:0`), когда `.periods` невидим (экраны
«Счета»/«Настройки»/«Бюджеты»), не «прыгает» в произвольную точку.

## Известные ограничения

- Растяжение/сжатие стеклянного индикатора переключателя, а также
  визуальная проверка в реальном iPhone/Safari PWA не проводились в этой
  сессии — только в браузере предпросмотра; используются широко
  поддерживаемые CSS-свойства (`transform`, `backdrop-filter` с fallback
  через `@supports`), деградация безопасна.
- Синтетические DOM-события (`dispatchEvent(MouseEvent)`) не всегда
  надёжно триггерят внутренний обработчик наведения Chart.js в headless-
  окружении предпросмотра — корректность содержимого tooltip проверена
  напрямую через публичный API Chart.js (`setActiveElements`) с реальными
  данными карточки; поведение по реальному тапу/клику пользователя не
  проверялось на физическом устройстве в этой сессии.
