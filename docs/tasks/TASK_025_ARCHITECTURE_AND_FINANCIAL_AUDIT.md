## 1. Executive summary

Приложение **считает деньги правильно в своём ядре**. Все ключевые финансовые
инварианты, проверенные на контролируемом наборе данных, выполняются: общий
капитал равен сумме балансов учитываемых счетов, внутренний перевод капитал не
меняет, сумма категорий равна общему итогу за период, редактирование даты
переносит операцию между периодами, удаление корректно пересчитывает все
агрегаты, пустой период даёт нули без `NaN`. Главная, Аналитика, Бюджеты и
детализация категории дают **одинаковые числа за одинаковый период**.

Проблемы находятся **не в ядре, а в слоях вокруг него**:

1. **Нет слоя селекторов.** `raw data → UI` вместо
   `raw data → normalized → selectors → UI`. Расчёты живут прямо внутри
   render-функций, поэтому одна и та же величина реализована 2–6 раз с разными
   соглашениями о границах периода.
2. **Экран «Статистика» практически не работает** — он читает несуществующие
   поля операции (`t.categoryId` вместо `t.cat`, `cat.icon` вместо `cat.emoji`),
   теряет последний день каждого месяца/года и сдвигает месячные столбцы на
   месяц назад из-за `toISOString()` над локальными датами. Это самый
   запущенный участок кодовой базы.
3. **Сохранение может тихо провалиться.** `AF.Store.save()` честно возвращает
   ошибку при переполнении `localStorage`, но `save()` в `index.html` этот
   результат выбрасывает — пользователь ничего не видит. Учитывая, что чеки
   хранятся как data-URL в той же записи, это реальный сценарий потери данных.
4. **Даты хранятся как `YYYY-MM-DD`, а разбираются как UTC** и сравниваются с
   локальными границами периода. В UTC+ зоне (Мадрид) это безвредно, в любой
   UTC− зоне каждая операция уезжает на день назад, а 1 января — в предыдущий
   год.

### Причина бага с пропадающими годами — найдена и воспроизведена

**Код экрана детализации категории корректен.** Навигация по годам, границы
года, фильтрация и подсчёт проверены и в программном, и в реальном
кликовом пути — ошибок нет (см. §8.1).

Симптом воспроизводится точно при **расхождении идентификаторов категории**:
операции старых лет лежат под **другим `categoryId`**, чем тот, с которым открыт
drill-down, при том что пользователю обе категории видны как «Продукты».
Экран фильтрует **строго по id** (`catTxIds.includes(t.cat)`), никогда по имени
— поэтому старые годы дают ровно `€0 · 0 операций · пустой список`.

Воспроизведение 1-в-1 (§8.2):

```
2026 => Всего: −€120 · 1 операция
2025 => Всего: −€0 · 0 операций
2024 => Всего: −€0 · 0 операций
2023 => Всего: −€0 · 0 операций
```

Механизмы, которые могли развести id (все существуют в коде):
`ensureCat()` создаёт новую категорию при любом несовпадении имени;
до `TASK_015` round-trip собственного CSV-экспорта создавал категорию с
буквальным именем «Продукты / Супермаркеты»; `ensureCat` ищет только внутри
своего типа, поэтому одноимённые «Продукты» для расхода и дохода — две разные
категории; `resolveCatSub` может увести операцию на родителя подкатегории.

**Чтобы подтвердить это на реальных данных**, в §8.3 приведён read-only
диагностический сниппет для консоли — он не меняет ничего и печатает
покрытие по годам для каждой категории.

## 2. Общее состояние архитектуры

### 2.1 Что есть

```
js/core/        result.js, app_info.js
js/database/    store.js            — репозиторий поверх localStorage
js/services/    17 файлов           — чистые функции, без DOM
index.html      6260 строк          — разметка + CSS + ВСЯ остальная логика (стр. 2597–6255)
tests/          12 файлов, 887 проверок
```

Слоистость **заявлена и частично реализована**: сервисы действительно чистые,
не трогают DOM/`localStorage` и покрыты Node-тестами. `AF.Store` — единственная
точка доступа к хранилищу, UI в `localStorage` напрямую не ходит (проверено).

### 2.2 Чего нет

**Нет слоя селекторов.** Между `state` и разметкой нет промежуточного уровня.
Render-функции сами фильтруют `state.tx`, сами считают границы периода, сами
агрегируют и тут же формируют HTML. Прямое следствие — расчёт одной величины
существует в нескольких экземплярах:

| Величина | Реализации |
|---|---|
| Границы периода | `AF.Services.Period.range` · `catTxRange` · `anaRange` · `rangeBack` · `budgetMonthRange` · `statsRange` — **6 штук** |
| «Потрачено по категории за период» | `budgetSpent` (index.html, с конвертацией) · `AF.Services.Budget.spent` (без конвертации) · `HealthScore._catSpent` (без конвертации) — **3 штуки, 2 разных ответа** |
| Разбивка по категориям | `AF.Services.Analytics.byCategory` · инлайн в `renderAnaPie` · инлайн в `renderDetail` · инлайн в `buildStatsOverview` |
| Сравнение периодов | `AF.Services.Analytics.compare` · `renderAnaCompare` |
| Проверка «операция в диапазоне» | `inPeriod` · `inAnaRange` · `inRange` — три идентичные функции |

**Часть сервисов не подключена.** `AF.Services.Budget` не вызывается из
`index.html` ни разу (проверено grep'ом по всем алиасам) — это мёртвый код с
реализацией, **отличающейся** от живой. `AF.Services.Analytics.byCategory` /
`topCategories` / `compare` тоже фактически не используются.

### 2.3 Что сделано хорошо

- Инвариант совместимости сервисов (`TASK_015 §0`): каждый новый сервис
  вызывается через защитный хелпер с деградацией — приложение не падает при
  рассинхронизации файлов на CDN. Это единственная действительно
  дисциплинированная часть архитектуры и её следует сохранить.
- `AF.Store.migrate()` идемпотентен и является единственной точкой входа
  **всех** путей загрузки данных (старт, restore `.afb`, импорт JSON, импорт CSV).
- Чистые сервисы без DOM/`localStorage` реально тестируемы в Node.
- Переводы корректно исключены из income/expense самой моделью данных
  (`type==='transfer'` — отдельный тип, а не пара записей).

## 3. Точная карта движения данных

```
localStorage['finance_app']  (одна JSON-запись; сюда же чеки как data-URL)
        │
        ▼
AF.Store.load() → JSON.parse → Object.assign(defaults(), raw) → migrate()
        │                                                          ├─ дефолты счетов
        │                                                          ├─ TxMeta.normalizeTx
        │                                                          └─ Security.normalize
        ▼
 window.state          ← ЕДИНСТВЕННЫЙ мутируемый глобальный объект
        │
        ├─ seedCategories()      (только на чистом старте)
        │
        ├── глобальный период:  anchor / period / customFrom / customTo
        │
        ▼
render()  ──► updateHome → renderRecent          ── inPeriod → periodRange → Period.range
          ├─► renderFinanceCard                  ── periodRange + FinanceCard.totals/capitalChange
          ├─► renderAnalytics                    ── periodRange + rangeBack + inAnaRange
          ├─► renderBudgets                      ── budgetMonthRange (СВОЙ расчёт месяца)
          └─► renderAccountsScreen               ── Account.balance/distribution

вне render():
   openCatTx / renderCatTx                       ── catTxRange (СВОЙ расчёт, свой anchor)
   renderDetail  (детализация счёта)             ── свой detailAnchor, свой месяц
   openStats / buildStats*                       ── statsRange (СВОЙ расчёт, привязан к new Date())
   openHealth                                    ── HealthScore._mr (СВОЙ расчёт месяца)
   openCalendar / processAutoPost                ── Forecast.occurrencesBetween

запись:
   saveTx / delTx / saveBudget / … → state.tx.push|filter|Object.assign
        → save() → AF.Store.save() → localStorage.setItem
                     └── Result.err при квоте ─── ⛔ РЕЗУЛЬТАТ ВЫБРАСЫВАЕТСЯ
```

**Единый источник истины для данных — да** (`state` один, `AF.Store` один).
**Единый источник истины для расчётов — нет** (см. §2.2).
**Единый источник истины для периода — нет:** глобальный `anchor`/`period`
используют Главная, Аналитика и Бюджеты; у детализации категории, детализации
счёта, Статистики и Health Score — собственные, независимые якоря периода.

### C-1 · Critical · Тихий провал сохранения при переполнении `localStorage`

- **Файлы:** `index.html:2721`, `js/database/store.js:84-93`
- **Функции:** `save()`, `AF.Store.save()`
- **Воспроизведение:** сделать `localStorage.setItem` бросающим
  `QuotaExceededError` → выполнить `save()`.
- **Ожидание:** пользователь видит явную ошибку, операция не считается сохранённой.
- **Факт (замер):** `AF.Store.save()` возвращает
  `{"ok":false,"error":"Не удалось сохранить данные"}`, `save()` этот результат
  **игнорирует**, пользователю показывается обычный тост «Расход добавлен ✓».
  В памяти операция есть, в хранилище — нет. После перезагрузки она исчезает.
- **Риск для данных:** **прямая потеря пользовательских данных без уведомления.**
  Сценарий не гипотетический: фото чеков сохраняются как data-URL в **той же**
  записи `finance_app`, а лимит `localStorage` — 5–10 МБ. Несколько десятков
  чеков достаточно. Провал одного `setItem` означает, что не сохранились **все**
  накопленные изменения состояния, а не только последнее.
- **Исправление:** `save()` должен проверять `Result` и при ошибке показывать
  блокирующее сообщение (не тост), не закрывать форму и предлагать выгрузку
  резервной копии. Отдельно — вынести чеки из основной записи (IndexedDB) либо
  жёстко ограничить их число/размер.
- **Тесты:** юнит на `Result` из `AF.Store.save` при бросающем `setItem`;
  статический тест, что `save()` не игнорирует возвращаемое значение.

### H-1 · High · Детализация категории показывает €0 за годы, где операции есть

- **Файлы:** `index.html:3212-3269`, `index.html:5638-5686`
- **Функции:** `renderCatTx()`, `openCatTx()`, `ensureCat()`, `resolveCatSub()`, `resolveCatPath()`
- **Воспроизведение:** операции 2023–2025 с `cat:'c_dup1'` (имя «Продукты /
  Супермаркеты»), операции 2026 с `cat:'food'` (имя «Продукты») → открыть
  детализацию «Продукты» → режим «Год» → листать назад.
- **Ожидание:** годы с операциями этой категории показывают их.
- **Факт:** `2026 → −€120 · 1 операция`, `2025/2024/2023 → −€0 · 0 операций`
  — **точное совпадение с сообщением пользователя.**
- **Причина:** `renderCatTx()` фильтрует
  `state.tx.filter(t => t.type===ty && catTxIds.includes(t.cat) && inAnaRange(t,r))`
  — **строго по id категории**. Расчёт года при этом корректен (проверено
  отдельно, §8.1). Идентификаторы могли разойтись через `ensureCat()`
  (создаёт новую категорию при любом несовпадении имени, ищет только внутри
  своего типа), через pre-`TASK_015` round-trip собственного CSV-экспорта
  (колонка «Категория» содержит «Категория / Подкатегория» — до `TASK_015`
  это имя создавалось буквально), либо через `resolveCatSub`, уводящий
  операцию на родителя подкатегории.
- **Риск для данных:** данные **не потеряны**, но недоступны и не учитываются
  ни в drill-down, ни в бюджете этой категории — пользователь видит заниженные
  расходы.
- **Исправление:** (а) не молчать — при `0 операций` за период, где у
  **других** категорий операции есть, показывать подсказку; (б) дать в
  «Категориях» операцию слияния двух категорий с переносом `cat` у операций;
  (в) сделать поиск дублей по нормализованному имени частью `migrate` (только
  предупреждение, без автослияния).
- **Тесты:** тест «drill-down по id не находит операции с другим id при
  одинаковом имени» (фиксирует поведение); тест слияния категорий; тест
  идемпотентности `ensureCat` при повторном импорте того же CSV.
- **Что нужно от пользователя:** запустить сниппет §8.3 и прислать вывод —
  он однозначно покажет, это ли причина.

### H-2 · High · Экран «Статистика» читает несуществующие поля операции

- **Файлы:** `index.html:5992, 5997, 6098, 6150, 6000, 6164`
- **Функции:** `buildStatsOverview()`, `buildStatsRecords()`, `buildStatsHabits()`
- **Воспроизведение:** внести любые расходы → открыть Профиль → Статистика.
- **Ожидание:** «Топ категории расходов» заполнен, «Самая частая категория»
  названа, у крупнейших операций иконки категорий.
- **Факт (замер):** `"Нет данных за период"` в топе категорий,
  `"—"` в самой частой категории, `📦` вместо иконок — **всегда, при любых данных**.
- **Причина:** операции хранят категорию в `t.cat`; код читает `t.categoryId`
  (`if(t.categoryId)` — всегда `undefined`). Дополнительно `cat.icon` — категории
  хранят `emoji`, поля `icon` нет, поэтому `cat.icon||'📦'` всегда даёт `📦`.
- **Риск:** неверная (пустая) аналитика; данные не портятся.
- **Исправление:** `t.categoryId` → `t.cat`, `cat.icon` → `cat.emoji` в четырёх
  местах; правильнее — перевести экран на `AF.Services.Analytics.byCategory`.
- **Тесты:** тест «топ категорий не пуст при непустых расходах»; статический
  тест, что `t.categoryId` не встречается в `index.html`.

### H-3 · High · «Статистика» теряет последний день месяца и года

- **Файлы:** `index.html:5879-5898`
- **Функции:** `statsRange()`, `statsTxInRange()`
- **Воспроизведение:** расходы `2026-07-15` (10 €), `2026-07-31` (99 €),
  `2026-12-31` (77 €) → Статистика, режим «Месяц» и «Год».
- **Ожидание:** месяц — 3 операции / 109 €; год — 4 операции / 186 €.
- **Факт (замер):** месяц — **2 операции / 10 €**; год — **3 операции / 109 €**.
- **Причина:** `to` строится как `new Date(y, m+1, 0)` и `new Date(y, 11, 31)`
  — это **00:00:00** последнего дня, а операция этого дня разбирается как
  01:00/02:00 локального времени и оказывается **позже** верхней границы.
  Для сравнения `AF.Services.Period` задаёт `23:59:59.999` и считает верно.
- **Риск:** систематически заниженные обороты, средние, рекорды и топы.
- **Исправление:** перевести `statsRange()` на `AF.Services.Period.range()`.
- **Тесты:** тест границ «31-е число входит в месяц» и «31 декабря входит в год»
  для **каждой** функции диапазона в проекте.

### H-4 · High · Операции архивных счетов входят в доходы/расходы, но не в капитал

- **Файлы:** `js/services/account_service.js:23,26`, `js/services/finance_card_service.js:12-31`, `index.html:3356`
- **Функции:** `Account.active()`, `Account.totalCapital()`, `FinanceCard.totals()`, `budgetSpent()`
- **Воспроизведение:** счёт `old` в архиве (`isArchived:true`, `start:100`),
  расход 50 € по нему в текущем месяце; активные счета — расходы 100 € и 108 $.
- **Ожидание:** согласованность между «изменением капитала» и «потоком» в одной
  и той же карточке.
- **Факт (замер):** капитал = **−200 €** (архивный счёт исключён), расходы
  Аналитики и Главной = **250 €** (расход архивного счёта включён),
  `budgetSpent('food')` = **250 €**.
- **Причина:** капитал считается по `active()`, а income/expense/бюджеты
  фильтруют только по типу и дате, не по состоянию счёта.
- **Риск:** карточка на Главной внутренне противоречива — «поток за месяц»
  не сходится с «изменением капитала»; бюджет расходуется операциями, которых
  «нет» в капитале.
- **Исправление:** принять решение на уровне продукта и применить **везде
  одинаково** — либо архивные счета целиком исключаются из всех агрегатов,
  либо целиком включаются. Полумеры порождают именно этот класс расхождений.
- **Тесты:** инвариант «поток за период = изменение капитала за период» на
  наборе с архивным счётом (сейчас падает).

### H-5 · High · Даты `YYYY-MM-DD` разбираются как UTC, а сравниваются с локальными границами

- **Файлы:** `index.html:2805, 3124, 3352, 3357, 4332, 4348, 5912`,
  `js/services/account_service.js:11`, `js/services/budget_service.js:9`,
  `js/services/health_score_service.js:14-15`,
  `js/services/finance_card_service.js:15`
- **Функции:** все `new Date(t.date)` против границ от `new Date(y,m,d)`
- **Воспроизведение (замер):** `Date.parse('2024-01-01')` = `1704067200000`,
  `+new Date(2024,0,1)` = `1704063600000`, разница **+1 ч** (Мадрид зимой).
  Симуляция по смещениям:

  | Смещение зоны | 1 янв 2024 попадает в 2024? | попадает в 2023? |
  |---|---|---|
  | UTC−12 … UTC−2 | **нет** | **да** |
  | UTC+0 … UTC+9 | да | нет |

- **Ожидание:** операция с датой 1 января относится к январю этого года в любой
  временной зоне.
- **Факт:** в любой зоне западнее Гринвича каждая операция смещается на день
  назад: 1-е число уходит в предыдущий месяц, 1 января — в предыдущий год.
- **Риск:** массовое «переползание» операций между периодами при смене зоны
  (поездка), включая ровно тот симптом, о котором сообщил пользователь.
  Данные не портятся, но отображаются не в тех периодах.
- **Исправление:** ввести **один канонический парсер** локальной даты
  (`parseLocalDate('YYYY-MM-DD') → new Date(y, m-1, d)`) в отдельном сервисе и
  заменить им **все** `new Date(t.date)`. Правильные образцы в коде уже есть:
  `new Date(t.date+'T12:00:00')` (строки 6132, 6155) и `t.date.slice(0,10)`.
- **Тесты:** прогон границ месяца/года при `TZ=America/New_York`,
  `TZ=Europe/Madrid`, `TZ=Pacific/Auckland`.

### H-6 · High · Одна нераспознанная дата обнуляет весь режим «Всё время»

- **Файлы:** `index.html:3226-3230`, `index.html:2999-3002`, `index.html:5896`
- **Функции:** `catTxRange()` (ветка `all`), `capPoints()` (ветка `all`), `statsRange()` (ветка `all`)
- **Воспроизведение:** добавить одну операцию с `date:'не дата'` → детализация
  категории → режим «Всё».
- **Факт (замер):** `Всего: −€0 · 0 операций`, нижняя граница диапазона —
  `Invalid Date`; `capPoints('all')` возвращает пустой массив (график капитала
  пуст). Режим «Год» при этом продолжает работать.
- **Причина:** `Math.min(...state.tx.map(t=>new Date(t.date)))` — одно `NaN`
  отравляет минимум, `new Date(NaN)` даёт `Invalid Date`, все сравнения
  становятся `false`.
- **Риск:** внезапное «исчезновение всех данных» на нескольких экранах из-за
  одной битой записи. `parseDate()` при импорте CSV пропускает строку с
  неразобранной датой, но правка вручную/старый JSON такую запись пронесут.
- **Исправление:** отфильтровывать невалидные даты до `Math.min`; при
  отсутствии валидных — безопасный дефолт; операции с битой датой показывать
  отдельным предупреждением, а не молча терять.
- **Тесты:** «одна битая дата не обнуляет режим Всё/график капитала/Статистику».

### H-7 · High · `toISOString()` над локальными датами сдвигает ключи месяцев и дней

- **Файлы:** `index.html:5978, 6016, 6144, 6194, 3646, 3649`
- **Функции:** `buildStatsOverview()` (столбцы за 6 месяцев, тепловая карта),
  `buildStatsHabits()` (дни без трат), `buildAchievements()` (серия дней),
  `processAutoPost()` (дата авто-операции)
- **Воспроизведение (замер, Мадрид):**
  `new Date(2026,6,1).toISOString().slice(0,7)` → **`'2026-06'`**;
  сегодня `Wed Jul 29 2026`, а `new Date().toISOString().slice(0,10)` → **`'2026-07-28'`**.
- **Ожидание:** столбец «июл» показывает июльские расходы; сегодняшняя клетка
  тепловой карты — сегодняшняя.
- **Факт:** столбец с подписью «июл» суммирует операции **июня** (и так для
  всех шести столбцов); тепловая карта, «дни без трат» и «серия дней» сдвинуты
  на день назад.
- **Особо:** `processAutoPost()` пишет **дату самой операции** через
  `d.toISOString().slice(0,10)` — то есть авто-операции по регулярным платежам
  сохраняются в данные **на день раньше** срока в UTC+ зоне. Это единственное
  место в списке, которое портит **записанные данные**, а не отображение.
- **Риск:** неверная статистика; для `processAutoPost` — систематически
  неверные даты у автоматически созданных операций.
- **Исправление:** заменить `toISOString().slice(0,10)` на существующий в файле
  `isoDate()` (`index.html:2672`) — он строит ключ из локальных компонент и
  уже написан правильно.
- **Тесты:** «ключ месяца/дня, построенный из локальной даты, совпадает с
  локальным месяцем/днём» при UTC+ и UTC− зонах.

| `goals` | `savedAmount`/`targetAmount` | да | код достижений ждёт `currentAmount` — M-5 |
| валюта | символ (`'€'`), с нормализацией кодов | да | `Currency.norm` |

### 6.2 Ответы на вопросы постановки

- **Единый канонический формат даты?** Де-факто да, формально — нет: он нигде
  не задокументирован и не валидируется, а разбирается тремя разными способами.
- **Единый канонический формат суммы?** Да: `Number`, положительный, знак — в `type`.
- **Могут ли суммы быть строками?** На путях ввода — нет (`evalExpr`,
  `parseAmount`, `parseFloat` дают `Number`). При ручной правке `localStorage`
  или импорте чужого JSON — да, и это ничем не проверяется.
- **NaN / Infinity / −0?** `evalExpr` отсекает `NaN`/`Infinity` при вводе;
  `Currency.parse` возвращает `NaN` для мусора, и импорт CSV такую строку
  пропускает. Но на выводе `format()` не защищён (L-1).
- **Дубликаты id?** Возможны (M-8).
- **Битые ссылки на удалённые категории/счета?** Да. Удаление категории
  (`index.html`, редактор категорий) и удаление счёта (`5580`) **не проверяют
  наличие операций**. `catById` возвращает заглушку «Другое ❓», счёт —
  `undefined`, суммы при этом считаются в базовой валюте. Операции остаются в
  расчётах, но теряют принадлежность — **тот же класс, что H-1**.
- **Могут ли старые операции не проходить новые фильтры?** Да — по id категории
  (H-1) и по нераспознанной дате (H-6).

### 6.3 `SCHEMA_VERSION` и миграции

`SCHEMA_VERSION = 3`. `migrate()` **идемпотентна и без ветвлений по номеру
версии** — это осознанное решение (`store.js:7-10`) и оно верное: миграция
нормализует любое состояние. Разрушающих данные шагов в `migrate` нет
(проверено построчно): она только дозаполняет отсутствующие поля.

**Пробелы миграции:** не валидирует `tx.date`, не валидирует `tx.amount`,
не проверяет ссылочную целостность `cat`/`account`, не дедуплицирует id,
не сообщает о найденных проблемах. Все находки H-1/H-6/M-8 прошли бы именно
здесь.

## 8. Диагностика бага с годами

### 8.1 Код экрана детализации категории — проверен, ошибок нет

Проверены оба пути: программный (прямая установка `catTxAnchor`) и **реальный
кликовый** (клики по `#catTxSeg button[data-m="year"]`, `#catTxPrev`,
`#catTxNext`). Набор: операции категории «Продукты» в 2021, 2022, 2023
(+31 декабря), 2024 (+1 января, +29 февраля), 2025, 2026.

```
клик «Год»  → 2026 => −€100 · 1 операция
‹           → 2025 => −€100 · 1 операция
‹           → 2024 => −€155 · 3 операции   (в т.ч. 1 янв и 29 фев)
‹           → 2023 => −€111 · 2 операции   (в т.ч. 31 дек)
‹           → 2022 => −€100 · 1 операция
‹           → 2021 => −€100 · 1 операция
‹           → 2020 => −€0   · 0 операций   (данных нет — корректно)
```

Цепочка по пунктам постановки: категория выбирается по id из
`row.dataset.cat`; режим — из `data-m`; год — из `catTxAnchor.getFullYear()`;
`start/end` — `new Date(y,0,1)` … `new Date(y,11,31,23,59,59)`; фильтрация —
`type` + `includes(cat)` + диапазон; количество — `list.length`; итог —
`Σ txBase(t)`; группировка — по `t.date.slice(0,10)`; три карточки — сумма/
число месяцев. Экран **использует собственную логику** (`catTxRange`), а не
`AF.Services.Period` (M-1), но результат для года совпадает с сервисным.

### 8.2 Воспроизведение симптома

Единственный сценарий, дающий **точное** совпадение с сообщением пользователя,
— расхождение id категории между годами:

```
2026 => Всего: −€120 · 1 операция
2025 => Всего: −€0 · 0 операций
2024 => Всего: −€0 · 0 операций
2023 => Всего: −€0 · 0 операций
```

Второй сценарий, дающий тот же визуальный результат для **режима «Всё»** (не
для «Год») — одна нераспознанная дата (H-6).

### 8.3 Read-only диагностика для production

Открыть https://adar4026.github.io/finance/ → консоль → вставить. **Ничего не
меняет**, только читает и печатает:
