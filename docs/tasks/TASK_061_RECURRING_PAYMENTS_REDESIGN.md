# TASK_061 — Редизайн экрана «Регулярные платежи»

**Статус:** DONE

## Контекст

Пользователь (2026-10-16): переработать экран «Регулярные платежи»
(drawer → «Регулярные платежи», `#recurOverlay`) в современном
минималистичном iOS-стиле LexMoney: стрелка «назад» вместо `×`, кнопка
`+` в заголовке, карточка ежемесячных обязательств, аккуратный список
ближайших списаний, приостановка платежа — без новой системы стилей и
хранения, без двойного учёта.

## Исследование (до изменений)

- Экран: `#recurOverlay` → `.detail-sheet`, заголовок «🔁 Регулярные
  платежи» + `×` (`#recurClose`), список `#recurList` из `eventRow()`
  (общий со строками Календаря), пунктирная `.set-btn` «＋ Добавить

  тап по фону, глобальный Escape. Истории браузера экран не использует.
- Навигация: единственный экран с историей — шторка операции
  (`history.pushState({txSheet:true})` + `popstate`, TASK_013). Каркас
  «отдельного экрана» со стрелкой назад — `.catx-page/.catx-nav/.catx-back`
  (TASK_041/TASK_060).
- Модель: регулярный платёж = напоминание `state.reminders[]`
  `{id,title,amount,type,dueDate:'YYYY-MM-DD',repeatType,categoryId,
  accountId,autoPost,lastPosted,isActive,done,createdAt}`.
  `repeatType ∈ none|daily|weekly|monthly|yearly`. Поле **`isActive` уже
  есть** (`activeReminders()` фильтрует `isActive!==false`; прогноз и
  авто-проводка его учитывают), но UI для него нет, а `saveReminder()`
  всегда пишет `isActive:true`.
- Сумма платежа — в валюте его счёта (авто-проводка кладёт `r.amount` на
  `r.accountId`, иначе на первый счёт); на экране сейчас форматируется в
  базовой валюте (`num`) — неточно для валютных счетов.
- Даты: `AF.Services.Forecast` — `new Date('YYYY-MM-DD')` (UTC-полночь) и
  итеративный `setMonth(+1)`: платёж 31-го «уплывает» (31 янв → 3 мар →
  3 апр …), 29 фев ежегодный → 1 мар навсегда. Тот же сервис питает
  Календарь, прогноз баланса и авто-проводку (`processAutoPost`, там
  `toISOString()` для даты операции).
- Удаление напоминания — без подтверждения (цели/счета/категории
  используют `confirm()`).
- Двойной учёт: регулярный платёж сам баланс не меняет; операции создаёт
  только авто-проводка (`autoPost`) с защитой `lastPosted` + `autoFrom`.
- Тесты: 38 файлов, базовая линия **3083 passed, 0 failed**.

## Цель

Экран «Регулярные платежи» в стиле LexMoney: лёгкая стрелка назад
(история + жест от края + fallback), `+` справа, карточка «Ежемесячные
расходы» (месячный и годовой эквивалент только активных расходных
платежей), список «Предстоящие списания» по ближайшей дате, приостановка /
возобновление, пустое состояние; корректные даты 29–31 / февраль /
високосный год.

**Как считается итог** (`AF.Services.Recurring.summary`): берутся только
повторяющиеся (`daily/weekly/monthly/yearly`), активные (`isActive!==false`)
расходные напоминания. Сумма платежа → целые центы базовой валюты
(валютный счёт — `Currency.toBase` по курсам приложения). Годовой
эквивалент = центы × повторов в году (ежедневно 365, еженедельно 52,
ежемесячно 12, ежегодно 1) — целое число; месячный = годовой / 12 с одним
округлением в конце. Это эквивалент обязательств, а не сумма списаний
текущего календарного месяца. Пример проверки в preview:
10 200 + 35,88 + 420 + 650 + 360 + 95,88 = 11 761,76 €/год → 980,15 €/мес.
Пересчёт — при каждом `renderRecurring()` (вызывается после добавления,
правки, удаления, паузы).

**Даты** (`AF.Services.Forecast`, публичный API прежний): `'YYYY-MM-DD'`
разбирается как локальная полночь (а не UTC); k-й повтор считается от
исходной даты с зажимом на последний день месяца (31 янв → 28/29 фев →
31 мар → 30 апр; 29 фев ежегодно → 28 фев / 29 фев) вместо накопительного
`setMonth(+1)`, который «уплывал» на 3-е число. Еженедельные/ежедневные —
по календарным дням (переход на летнее/зимнее время не сдвигает день).
Ближайшая дата — первый повтор ≥ сегодня; хранилище не меняется.
Сортировка стабильна: дата → название (ru) → id; «по сумме» — сумма в
базовой валюте ↓ → дата → название. Исправление дат действует и в
Календаре / прогнозе баланса / авто-проводке (один источник).

**Пауза:** существующее поле `isActive:false` — без новых полей и
миграции. Приостановленный платёж хранится, виден на экране, не входит в
итог, прогноз, Календарь и авто-проводку. Возобновление
(`Recurring.resumePatch`) при `autoPost` сдвигает `lastPosted` на последний
повтор до сегодняшнего дня — пропущенные за паузу операции задним числом не
создаются; сегодняшний и будущие повторы проводятся.

**Учёт финансов / двойной учёт:** экран и сервис ничего не пишут в
операции и баланс (проверено тестом: `state` не меняется). Добавление
регулярного платежа не создаёт операцию (preview: `tx` = 0 после
добавления/правки/паузы/удаления). Авто-проводка сохранена (`autoFrom`,
`lastPosted`, откат TASK_026); даты — `Recurring.autoPostDates` (локальный
день вместо `toISOString`), плюс защита «не более одной авто-операции за
месяц/год после `lastPosted`» — переход со старых «уплывших» дат (проведено
3 окт → 31 окт не дублируется) и перенос даты после проводки не дают второй
операции в том же периоде.

`Currency.format(n, cur, {cents:true})` — новый необязательный режим
(«€7,90», целые — «€20»; как `amount_input_service`), без опций — прежнее
поведение. `sw.js` `finance-v192` → `finance-v193`, сервис в precache.

- Сумма платежа хранится в валюте счёта без собственного поля валюты (как
  и раньше); итог переводится в базовую валюту по курсам приложения.
- Еженедельный годовой эквивалент — 52 недели (по постановке), ежедневный —
  365 дней.
- Жест от края работает в standalone-PWA; в Safari-вкладке системный
  свайп браузера сам делает `history.back()` → экран закрывается через
  `popstate`.
- Включение `autoPost` у давнего напоминания по-прежнему проводит повторы
  с `dueDate` (существующее поведение формы, вне границ задачи).
- Сортировка «По сумме» не запоминается между открытиями (без новых
  настроек в хранилище).

## Релизные проверки (2026-10-17, по запросу пользователя перед публикацией)

### 1. Авто-проводка: защита от дублей

Старый код (до TASK_061) воспроизведён в тесте и в симуляции «открываем
приложение каждый день» в Europe/Madrid, Atlantic/Canary,
America/New_York, Asia/Tokyo. Найдено:

- старый `lastPosted` — «старая» дата k-го повтора: летом для платежа,
  созданного зимой (UTC+1/+2), **на день раньше настоящей** (`toISOString`
  от 01:00 местного времени), у 29–31 числа — «уплывшая»;
- правило «одна операция за месяц/год» закрывало ежемесячные и ежегодные,
  но **ежедневные и еженедельные** после перехода получили бы **дубль**
  последнего проведённого повтора (13 окт по старому «12 окт»);
- попутно: сам старый код летом повторно проводил такие повторы при каждом
  открытии (история пользователя не меняется, операции не удаляются).

Исправлено: `Recurring.legacyPostedIndex/effectiveLastPosted` находят по
старому алгоритму номер k уже проведённого повтора и переводят
`lastPosted` в новую дату k-го повтора; `processAutoPost` однократно
сохраняет это с маркером `lastPostedV:2` (новое необязательное поле
напоминания — нужно, чтобы новый `lastPosted` никогда не перечитывался как
старый; бэкап/экспорт сохраняют напоминания как есть, старые версии поле
игнорируют). Все места, пишущие `lastPosted` (проводка, возобновление,
повтор из формы операции), ставят `lastPostedV:2`.

Результат: первый новый повтор = последний старый + 1 во всех поясах и
периодичностях; законные повторы не блокируются (ежедневно через переход
на летнее время, еженедельно через Новый год, 31-е через февраль, 29 фев
через високосные годы, догоняющая проводка после перерыва). Для 29–31 числа
старый код пропустил февраль, поэтому, например, 31 окт — законный 10-й
платёж (число авто-операций = число повторов), а не дубль. Тесты:
`tests/recurring_service.test.js` §5b (+109 проверок), в т.ч. перезапуск в
America/Los_Angeles. В реальном приложении (preview, Europe/Madrid):
еженедельный со старым «2026-10-12» → `lastPosted` «2026-10-13»,
`lastPostedV:2`, операций 0, повторный запуск — 0.

### 2. PWA и Service Worker

Production (GitHub Pages) отдаёт все файлы с `Cache-Control: max-age=600`.
Найдено:

- `fetch(e.request)` и `cache.addAll()` шли через HTTP-кэш браузера;
  перезагрузка (в т.ч. автоматическая `location.reload()` по
  `controllerchange`) перепроверяет только HTML, подресурсы берёт из
  кэша — **свежий HTML мог получить старый JS** (новый `index.html` со
  старым `forecast_service.js` падал бы на старте), а новый кэш
  `finance-v193` мог заполниться старыми копиями (смешанный офлайн-набор);
- в кэш попадали и ответы с ошибкой (404/500).

Исправлено:

- все 32 локальных скрипта подключены как `js/…?v=193` (= номер кэша):
  HTML всегда загружает «свой» JS — и свежий, и взятый из кэша;
- `sw.js`: precache — версионные URL скриптов, `cache:'reload'` (мимо
  HTTP-кэша); навигация — `cache:'no-cache'` (HTML не из HTTP-кэша онлайн);
  в кэш только успешные ответы; офлайн-навигация без точного совпадения →
  `index.html`; `activate` удаляет старые кэши (как раньше);
- AGENTS.md, чек-лист релиза: номер `?v=` поднимается вместе с cache
  version; `tests/pwa_cache.test.js` (117 проверок) проверяет совпадение
  номеров, наличие в ASSETS и поведение SW в эмуляции (install / activate /
  fetch онлайн и офлайн);
- 7 существующих тестов, сверявших строку `<script src="…js">`, допускают
  `?v=N`.

Остаточный риск (вне контроля нового кода): в первые ≤10 минут после
деплоя страницей управляет старый SW `finance-v192`; смешение возможно
только при частичном вытеснении HTTP-кэша (HTML остался, JS — нет). Как
только новый SW активируется, он перезагружает страницу уже со своими
правилами.
