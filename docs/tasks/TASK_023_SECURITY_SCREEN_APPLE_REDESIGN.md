## 3. Найденная существующая архитектура (что реально есть)

### 3.1. Защитный код (PIN) — реальный, полностью рабочий

- `state.pinHash` — SHA-256 от `'af_pin_' + code` (`sha()`,
  `index.html:3680`), в открытом виде код не хранится.
- Машина состояний `pinStart(mode)` / `pinKey()` / `pinComplete()` /
  `pinError()` / `closePin()` (`index.html:3694–3720`) с режимами
  `set` / `change` / `disable` / `unlock`, экраном ввода `#pinOverlay`
  (клавиатура-кейпад, 4 точки, вибрация при ошибке).
- Блокировка на входе: `if(state.pinHash)pinStart('unlock')`
  (`index.html:5939`), у режима `unlock` скрыта кнопка «Отмена» и он не
  закрывается по Escape (`#pinOverlay` намеренно отсутствует в общем
  Escape-списке, `index.html:5580`).

**Вывод:** логика защитного кода реальна и переиспользуется целиком, ни
одна её строка не переписывается.

### 3.2. Face ID / биометрия — в приложении сейчас НЕТ

Поиск по `index.html` и `js/**`: ни `WebAuthn`, ни
`navigator.credentials`, ни `PublicKeyCredential`, ни какого-либо
упоминания биометрии — ноль совпадений. Функции не существует вовсе.

Честная (не имитирующая) реализация в вебе одна — **WebAuthn platform
authenticator**: `navigator.credentials.create/get` с
`authenticatorAttachment:'platform'` и `userVerification:'required'`. На
iOS (Safari 14+ и установленное PWA) это вызывает **настоящий системный
Face ID / Touch ID**, а не нарисованную заглушку. Доступность заранее
определяется штатным
`PublicKeyCredential.isUserVerifyingPlatformAuthenticatorAvailable()`.

**Границы честности, которые обязаны быть зафиксированы в UI и в
документации:**

- Это **локальная блокировка входа в приложение**, ровно того же класса,
  что существующий PIN (данные в `localStorage` ею не шифруются). Именно
  так и описан PIN в текущем экране («локальная блокировка приложения на
  этом устройстве»).
- Сервера у приложения нет, поэтому WebAuthn-assertion проверяется не
  криптографически на бэкенде, а фактом того, что платформенный
  аутентификатор вообще выдал подпись — а он не выдаст её без
  прохождения Face ID / Touch ID / кода устройства. Это реальная
  системная проверка пользователя, но не серверная аутентификация; в
  тексте экрана не заявляется большего.
- Если `isUserVerifyingPlatformAuthenticatorAvailable()` вернул `false`
  (или API нет вовсе — не-secure-context, старый браузер, десктоп без
  биометрии) — строка Face ID переводится в честное **недоступное**
  состояние с пояснением, переключатель `disabled`. Никакой имитации.

### 3.3. «Запрашивать» (когда требовать код) — в приложении сейчас НЕТ

Блокировка сегодня срабатывает **только на холодном старте**
(`index.html:5939`). Возврата в приложение из фона она не отслеживает.
Чтобы настройка «Запрашивать» была настоящей, а не декоративной, нужен
реальный учёт времени неактивности — иначе выбор «Через 15 минут» ничего
бы не менял, что и есть «фальшивая безопасность», прямо запрещённая
постановкой.

Существующая точка опоры: `document.addEventListener('visibilitychange')`
уже есть (`index.html:5941`, догоняет авто-операции) — новый обработчик
добавляется рядом, не заменяя его.

### 3.4. Виджеты — в приложении и в PWA их НЕТ

- `manifest.json` не содержит поля `widgets`, в проекте нет ни одного
  файла виджета, нет обмена данными с виджетами.
- Ни один код приложения не читает и не пишет настройку доступа виджетов.

**Вывод:** «Разрешить виджетам доступ к данным» реализуется как честное
информационное **disabled**-состояние (переключатель выключен, `disabled`,
`aria-disabled`, рядом пояснение). Настройка **не** сохраняется — хранить
флаг, который ни на что не влияет, значило бы заявить несуществующую
защиту. Требование пользователя на этот счёт прямое и допускает такой
исход.

### 3.5. «Скрывать суммы» — реальная существующая функция экрана

Сейчас на экране безопасности есть вторая строка «🙈 Скрывать суммы»
(`state.hideAmounts`). Референс её не содержит. Функция реальна и
используется (`#fcEye` на Главной, `#capEye2` на «Счетах», `render()`),
поэтому она **не удаляется**, а выносится в отдельную карточку под
заголовком «Приватность» — тот же визуальный язык, ноль потери
функциональности. Удалять существующую точку входа, о которой
постановка не просила, — выход за границы задачи.

## 4. Цель

Полностью переработать существующий экран «Безопасность» под референс —
светлый Apple-style полноэкранный экран в едином языке Профиля/Счетов/
Бюджетов — **и одновременно** довести до реального рабочего состояния
заявленные на нём настройки: защитный код (уже реальный), биометрия

## 6. Критерии готовности

- Экран визуально соответствует референсу по композиции: серый фон,
  круглая кнопка «Назад» с обводкой, центрированный заголовок, крупный
  подзаголовок, две основные белые карточки с крупным радиусом, тонкие

- Единый вид рядом с Профилем/Счетами/Бюджетами (те же токены).
- Защитный код: включение, создание, повтор, изменение, отключение и
  проверка на входе — реально работают через существующую машину
  состояний.
- Face ID: при наличии платформенного аутентификатора реально
  регистрируется и реально запрашивается при разблокировке; при
  отсутствии — честное `disabled` с пояснением, без имитации.
- Выключение кода гасит Face ID; включение Face ID без кода ведёт к
  созданию кода.
- «Запрашивать» открывает аккуратный выбор, значение сохраняется и
  переживает перезагрузку, и реально влияет на момент блокировки.
- Виджеты: честное disabled/info-состояние, ничего не сохраняется.
- Переключатели: `role="switch"` + `aria-checked`, доступны с
  клавиатуры (`Tab`/`Space`/`Enter`), видимый focus, плавная анимация,
  различимые on/off, бирюзовый акцент в активном состоянии.
- Возврат по кнопке «Назад» возвращает ровно на экран Профиля.
- Тёмная тема и мобильная ширина iPhone — без поломок.
- Все существующие тесты (709) проходят без регрессий + новые тесты.

### 8.2. Что реально работает, а что честно помечено недоступным

| Настройка | Статус | Как реализована |
|---|---|---|
| Защитный код | **реальная, существовавшая** | `state.pinHash` = SHA-256 c солью, машина `pinStart/pinKey/pinComplete`, блокировка входа. Переиспользована целиком, логика не переписывалась. |

| Face ID | **реальная, новая** | WebAuthn platform authenticator (`authenticatorAttachment:'platform'`, `userVerification:'required'`) — на iOS это системный Face ID/Touch ID. Доступность — `isUserVerifyingPlatformAuthenticatorAvailable()`. |
| Запрашивать | **реальная, новая** | Значение сохраняется, `shouldLock()` сравнивает простой с задержкой; отметка ставится на `visibilitychange`/`pagehide`. |
| Скрывать суммы | **реальная, существовавшая** | `state.hideAmounts`, тот же обработчик, что был. |
| Доступ виджетам | **недоступна честно** | Виджетов у PWA нет — переключатель `disabled`, пояснение под строкой и отдельная сноска; настройка **не сохраняется**. |

синхронизации на экране нет.

## 10. Известные ограничения

1. **Реальный круг WebAuthn не проверен в этой сессии.** Безголовый
   браузер превью сообщает `isUserVerifyingPlatformAuthenticatorAvailable()
   = true`, но `navigator.credentials.create()` в нём зависает — системный
   диалог показать негде. Поэтому проверены: определение доступности,
   оба состояния строки Face ID, правила зависимостей, показ кнопки
   «Разблокировать Face ID» на экране ввода кода и то, что при неудаче
   ничего не включается. Сам системный запрос Face ID и разблокировку по
   нему нужно подтвердить на реальном iPhone (Safari или установленное
   PWA) — тот же класс открытого пункта, что ручные iPhone-проверки
   `TASK_015`/`TASK_017`.
2. **Клавиатурные нажатия не удалось доставить в страницу** инструментом
   превью (события `keydown` до документа не доходят — пане не передаётся
   фокус). Клавиатурная доступность подтверждена структурно: нативные
   `<button type="button">` с `tabIndex 0`, реальный фокус, рабочий
   `:focus-visible`, сохранение фокуса после перерисовки. Активация
   пробелом/Enter для нативной кнопки обеспечивается самим браузером.
3. Настройка «Запрашивать» опирается на `visibilitychange`/`pagehide`.
   Если iOS выгрузит веб-вью без этих событий, отметки не будет и
   приложение заблокируется — намеренный fail-secure выбор.
