# TASK_063 — Адаптивная компактная нижняя навигация (Instagram / Revolut)

**Статус:** DONE — релиз **v2.4.0** (2026-10-17), cache `finance-v196`. Проверка на реальном iPhone не выполнялась (см. «iOS»).

## Контекст

Капсула Liquid Glass (`TASK_062`/`062A`) всегда в полном размере. Нужно
поведение как в Instagram/Revolut: прокрутка вниз — панель компактнее,
вверх — снова полная. Контент всех пяти экранов прокручивается в одном
контейнере `#scrollArea` (TASK_006; не `window`), на нём уже есть один
passive-обработчик (`.topbar.scrolled`) — новый слушатель не добавляется,
расширяется существующий.

## Цель

Состояния Expanded / Compact у существующей `.nav` без новой навигации,
без изменения маршрутов, вкладок, `navDrag`, материала стекла.

## Границы работы

Разрешено: `index.html` — CSS `.nav.compact`, токен
`--navh-compact`, чистый модуль `navCompact` (решение по направлению),
подключение к существующему scroll-обработчику `#scrollArea`, вызов
`navCompact.expand()` в `showScreen()`; перенос `#addBtn` к заголовку
«Записи» (дополнение 2); новый тест `tests/bottom_nav_compact.test.js`,
правка тестов, фиксировавших прежнее место «＋»; документация.

Запрещено: `navDrag`, `moveNavIndicator`, разметка вкладок, маршруты,
бизнес-логика, стекло/цвета TASK_062, кнопка «＋» внутри капсулы, шестая
вкладка, новые зависимости, версия/SW до разрешения на публикацию.

## Требования

1. Expanded при загрузке, у верхней границы (≤ 24px), при прокрутке вверх,
   при смене вкладки, при фокусе клавиатуры внутри панели, когда
   прокручивать нечего.
2. Compact — при устойчивой прокрутке вниз (накоплено ≥ 12px в одну
   сторону, и позиция > 56px); Expanded — при накопленных ≥ 12px вверх.
   Смена направления сбрасывает накопление (гистерезис); dy = 0 — ничего.
3. Позиция зажимается в [0, max] — rubber-band iOS у краёв не переключает.
4. Во время drag pill состояние не меняется.
5. Compact: высота 64 → 54px, вертикальный padding 7 → 4px (горизонтальный
   7px — геометрия `navDrag`); внешняя капсула сужается (см. дополнение), подписи — opacity/max-height → 0, иконка
   scale .92, pill по высоте следует за капсулой; все 5 вкладок 50×44px. ~~«＋» следует за правым краем капсулы и опускается
   на разницу высот~~ — заменено дополнением 2: «＋» у заголовка «Записи», в анимации не участвует.
6. Анимация ≈ 220ms; `prefers-reduced-motion` — без анимации.
7. Резерв `.scroll-area` padding-bottom не меняется (рассчитан на Expanded —
   последняя строка не перекрывается ни в одном состоянии).

## Диагностика «первой прокрутки» — продолжение (2026-10-17, новая сессия)

### Найдено и исправлено: первое движение на новой высоте терялось

Воспроизведено детерминированно (Dev Preview, 390): «Все записи» прокручены к верху (последнее
scroll-событие: `max=3236`) → «Главная»: `scrollTop` 0 → 0, scroll-события нет, реальный
`max=902`, а `lastMax` остался 3236 → прокрутка вниз одним событием на 450px → `step()` видит
`max ≠ lastMax`, считает событие перерисовкой (`relayout`) и не сворачивает панель; Compact
наступал только со второго события. При плавной прокрутке терялось одно событие, при одиночном
скачке (PageDown/пробел, клик по полосе прокрутки, короткий flick с редкими событиями) — весь
первый жест. Тот же механизм на свежей загрузке: `lastMax` берётся при запуске скрипта, пока
контент ещё дорисовывается.

Причина: точка отсчёта (`lastY`/`lastMax`) обновлялась только scroll-событиями, а прокручиваемая
высота меняется и без них. Исправление: `navCompact.resync()` переустанавливает точку отсчёта по
текущему layout; вызывается `ResizeObserver` на `#scrollArea` и её дочерних блоках (`.subhead`,
экраны) — сразу после layout, раньше scroll-события от scroll anchoring (оно приходит с dy = 0).
Накопление жеста не сбрасывается, класс не трогается. Это не scroll-слушатель: единственный
scroll-обработчик `#scrollArea` прежний. Без задержек и без изменения порогов. Фикс §13
(anchoring) сохранён.

Проверено после фикса (Chromium, 390): `lastMax` сразу 902 после перехода; первый скачок вниз →
Compact; свежая загрузка → первая прокрутка вниз (одно событие) → Compact, вверх 20px → Expanded;
переход по 5 вкладкам из Compact — одно раскрытие, повторного сворачивания нет; 15 повторов
«вкладка → Главная → верх → скачок» — 15/15; 6 циклов вниз/вверх — последовательность классов
ровно `CECECECECECE`. Тест §14 (13 проверок), включая демонстрацию причины без `resync`.

### Свежая загрузка без ввода

Наблюдение с `document.readyState = loading`, 3с без ввода: 0 смен класса, 0 scroll-событий,
`scrollTop = 0`, Expanded (`max` растёт 0 → 902 по мере рендера, scroll-событий не вызывает).
Прежний «инерционный сдвиг после загрузки» из прошлой сессии не воспроизведён — по-прежнему

### Найдено и исправлено: перерисовка экрана засчитывалась как жест

Воспроизведено стабильно: Compact → клик по «Аналитика» → `showScreen()` →
`navCompact.expand()` запоминает `lastY=330` → `render()` строит новый экран:
`scrollHeight` 1611 → 1945, браузер (scroll anchoring) сам сдвигает
`scrollTop` 330 → 382 → scroll-событие с dy = +52px → панель снова Compact
через 23ms после раскрытия. Аналогично при drag на другую вкладку (сдвиг
330 → 288.5, дробное значение — признак anchoring).

Исправление (причина, не симптом): `navCompact.step()` хранит прошлую
прокручиваемую высоту `max = scrollHeight − clientHeight` (`lastMax`); если
она изменилась — сдвиг сделал браузер (anchoring, зажим при укорочении
контента, смена высоты viewport), событие только переустанавливает точку
отсчёта, состояние не меняется. Без задержек и без изменения порогов.
Тест §13 (3 проверки) на копии кода без фикса падает 3/3, с фиксом проходит.

После фикса (Dev Preview, 390): свежая загрузка — `scrollTop=0`, Expanded;
первая прокрутка вниз → Compact, вверх → Expanded; смена вкладки из Compact
на все 5 экранов → Expanded и остаётся (раньше «Аналитика» сворачивалась
обратно); реальный клик и drag в Compact — Expanded без повторного
сворачивания; 6 циклов подряд — без сбоев; 320/390 — геометрия прежняя.

### Не воспроизведено: инерционный сдвиг после свежей загрузки

В двух прогонах (в т. ч. первом, из прошлого отчёта) `scrollTop` менялся без
записей моего скрипта: шаги по 1px с замедлением (396 → 408) и плавный спуск
118 → 0 через 4с после окончания скрипта; `scrollHeight` при этом не менялся.
Профиль — инерция колеса/трекпада, т. е. реальный ввод в общей панели
браузера (её видит и может прокручивать пользователь). В коде приложения
программной прокрутки `#scrollArea` нет, кроме автопрокрутки при
перетаскивании счетов/категорий в режиме редактирования. С полным
мониторингом с первой миллисекунды (3 свежие загрузки, синтетическая и
настоящая wheel-прокрутка) — 0 посторонних сдвигов, 0 записей `scrollTop` из
кода. Реакция `navCompact` в тех прогонах была корректной (реальное движение
вверх ≥12px → Expanded). Источник ввода не доказан на 100% — зафиксировано
как «не воспроизводится при мониторинге», не как «устранено».

## iOS

Среды нет: на Mac только Command Line Tools — Xcode и iOS Simulator
(`simctl`) не установлены. Проверка на iOS **не выполнялась**.

### Инструкция для реального iPhone

1. Mac и iPhone в одной Wi-Fi сети; на Mac запущен dev-сервер сессии
   (`python3 -m http.server 8913 --directory /Users/MacPro/Projects/Finance`,
   слушает все интерфейсы).
2. В Safari на iPhone открыть `http://192.168.1.128:8913/` (IP Mac на момент
   проверки; проверить `ipconfig getifaddr en0`). Это не production.
   По http с LAN-IP Service Worker не регистрируется — для проверки навигации
   это не мешает; установленную PWA так проверить нельзя.
3. Аватар (боковая шторка) → «Все настройки» → строка «Демо-данные» →
   «Заполнить», подтвердить (данные только этого адреса).
4. Проверить:
   - медленная и быстрая (инерционная) прокрутка вниз → капсула сужается и
     становится ниже, подписи гаснут; вверх → раскрывается во время движения;
   - смена направления посреди анимации — без скачка;
   - rubber-band у верхнего края (≤24px — всегда полная) и у нижнего (отскок
     не раскрывает);
   - размытие/стекло во время изменения ширины — без мерцания и «чёрных»
     кадров;
   - тап по каждой из 5 вкладок в Compact; drag подложки в Compact;
   - «＋» справа от «Записи» на Главной: на одной линии, тап открывает форму,
     не меняется при сжатии капсулы; у капсулы кнопки нет;
   - светлая/тёмная тема (системная), повороты экрана;
   - Safari: появление/скрытие нижней панели браузера при прокрутке не
     должно дёргать капсулу (смена `clientHeight` → `relayout`, без
     переключения).
5. PWA (после публикации или через https-туннель): та же проверка в
   standalone, safe area 34pt → капсула в 20px от края.

### Оставшиеся риски iOS

- `backdrop-filter` в WebKit при анимации `left/right/height` может
  перерисовывать стекло каждый кадр — возможны подтормаживания на старых
  iPhone.
- Momentum-прокрутка WebKit может присылать scroll-события реже/пачками —
  порог 12px рассчитан на это, но проверено только в Chromium.
- Скрытие тулбара Safari меняет высоту viewport во время прокрутки: такое
  событие игнорируется (`relayout`) — одно событие направления теряется.
- Rubber-band iOS даёт отрицательный `scrollTop` у верха — зажим и
  `NAV_COMPACT_TOP` покрывают это, на устройстве не проверено.
