# TASK_011 — Standalone PWA: Bottom Strip Diagnosis

- **Номер:** TASK_011
- **Название:** Standalone Bottom Strip Diagnosis
- **Статус:** DONE

## Предыстория

`TASK_006`–`TASK_010` — пять последовательных попыток убрать белую полосу
внизу экрана на реальном iPhone. Все пять исправляли **разные слои
вслепую** (высоту `html`/`body`, `dvh`, `position:fixed`, фон
`#scrollArea`) и ни одна не помогла, потому что причина не была доказана —
менялся код, а не проверялась гипотеза. Эта задача останавливает такой
подход: сначала доказательство, потом исправление.

## Что уже доказано (без деплоя)

1. **Геометрия CSS корректна при работающем `viewport-fit=cover`.**
   Chromium всегда отдаёт `env(safe-area-inset-*)` = `0`, поэтому все
   прежние проверки в браузере предпросмотра были бессодержательны. Сделана
   копия приложения с подстановкой реальных значений iPhone
   (`inset-bottom:34px`, `inset-top:47px`) — замеры при 375×812:
   `html/body/.app/#scrollArea` — все `bottom = 812`, `.nav` —
   `bottom = 778` (ровно 34px над краем), фон `#scrollArea` серый до самого
   низа. **Зазора нет.** Значит при корректно применённом `cover` текущий
   CSS белую полосу дать не может.
2. **Исключён `manifest.json` как источник полосы.** `background_color` и
   `theme_color` = `#0f1115` (почти чёрный) — launch surface / фон PWA не
   может выглядеть белым.
3. **Исключён сбой процентной высоты `.app`** (известная особенность
   WebKit): симуляция `.app{height:auto}` даёт другой симптом — ломается
   прокрутка, белой полосы не появляется.
4. **`viewport-fit=cover` присутствует и никогда не терялся** — единственный
   `<meta name="viewport">` в документе, без изменений с самого начала.
   Гипотеза `TASK_010` о потерянном/переопределённом `cover` не
   подтвердилась.
5. **Найдено расхождение (к самой полосе отношения не имеет, но должно быть
   учтено отдельно):** `<meta name="theme-color">` переключается по
   **системной** `prefers-color-scheme`, а тема приложения — по
   `localStorage`/`data-theme`. Плюс `manifest.theme_color` (`#0f1115`)
   противоречит светлому `meta theme-color` (`#f4f6fb`).

## Что доказал пользователь на реальном устройстве

Проведены два дискриминирующих теста (без деплоя):

1. **Переключение темы приложения в тёмную → полоса становится чёрной.**
   ⇒ полоса **внутри страницы** и красится корневым фоном (`--bg`), а не
   системным `theme-color` и не внешним контейнером браузера.
2. **В обычном Safari полосы нет; воспроизводится только в установленной
   standalone PWA.**
   ⇒ проблема специфична для `display-mode: standalone`.

**Промежуточный вывод:** внутри standalone-вьюпорта существует нижняя
область, которую `.app`/`#scrollArea` не перекрывают, и там виден корневой
фон `--bg`. Требуются точные числа именно из standalone, которые
невозможно получить в Chromium.

## Этап 2: данные с реального iPhone (standalone)

Пользователь снял показания debug-панели на реальном iPhone в установленной
PWA (`navigator.standalone: true`, `BUILD debug-1`):

```
screen.height:      812   ← физический экран устройства
window.innerHeight: 759   ← фактический вьюпорт веб-вью
docEl.clientHeight: 759
visualViewport.height: 759
inset-top:    53
inset-bottom: 29

html/body/.app/#scrollArea — bottom: 759 (у всех, без расхождений)
.nav — bottom: 730 = 759 − 29 (ровно как и задумано)
```

**Расшифровка:** `812 − 759 = 53`, что **в точности** равно
`env(safe-area-inset-top)`. Все внутристраничные слои (`html`/`body`/
`.app`/`#scrollArea`) заканчиваются на `759` — т.е. покрывают вьюпорт
**полностью**, без единого пикселя расхождения. Значит корень проблемы —
не в CSS-слоях внутри страницы (что и объясняет, почему пять предыдущих
попыток, `TASK_006`–`TASK_010`, не могли сработать: они правили именно эти
слои). Полоса — это область **физически вне вьюпорта** (`759…812`),
которую браузер/веб-вью закрашивает цветом фона документа (поэтому она
меняется вместе с темой — так и было обнаружено пользователем на предыдущем
шаге).

## Настоящая причина

`<meta name="apple-mobile-web-app-status-bar-style" content=
"black-translucent">`. Это well-known поведение iOS в standalone-режиме:
при `black-translucent` веб-вью не растягивается на весь физический экран,
а получает высоту «экран минус статус-бар» (`812 − 53 = 759`), при этом
начинаясь от `y=0` — контент рисуется **под** полупрозрачным статус-баром
сверху, а внизу остаётся неиспользуемая полоса ровно той же высоты (53px),
которую сама страница закрасить не может, т.к. эта область не входит в её
вьюпорт вообще. Совпадение `53 = inset-top` — не совпадение, а подпись
именно этого механизма.

`viewport-fit=cover` тут ни при чём и работает корректно (что и
подтверждают ненулевые `inset-top`/`inset-bottom`, прочитанные через
`env()`) — `black-translucent` независимо от него сокращает сам вьюпорт.

## Исправление

- `index.html`, `<meta name="apple-mobile-web-app-status-bar-style">`:
  `black-translucent` → `default`. Веб-вью в standalone теперь занимает
  весь физический экран (`0…812`), высота вьюпорта увеличивается до
  реальной, низ страницы совпадает с физическим краем экрана — полоса
  исчезает. Статус-бар при `default` рисуется системой поверх обычного
  (непрозрачного) фона, `env(safe-area-inset-top)` станет `0` — `.topbar`
  (уже использующая `padding:max(10px,env(safe-area-inset-top))`)
  автоматически подстроится под меньший отступ без правок кода.
- Debug-сборка полностью удалена: файл `debug-safearea.js` удалён, строка
  его подключения в `index.html` убрана.
- `sw.js`: версия кэша `finance-v152-debug` → `finance-v152` (обычная,
  без отладочного суффикса).

## Проверки выполнены

- `grep` подтвердил: в `index.html` не осталось ссылок на
  `debug-safearea.js`; файл физически удалён из репозитория.
- Синтаксис инлайн-скрипта `index.html` — без ошибок.
- Браузер предпросмотра (375×812, светлая тема): debug-панель и

  консоли браузера нет. (В Chromium `env(safe-area-inset-top)` всегда `0`,
  поэтому визуальной разницы от смены `status-bar-style` здесь не будет —
  сам эффект специфичен для iOS standalone и проверяется только на
  реальном устройстве.)

## Известные ограничения / что важно пользователю

- iOS кэширует `apple-mobile-web-app-status-bar-style` **в момент
  добавления иконки на домашний экран**. После деплоя для корректной
  проверки нужно **удалить старую иконку PWA с главного экрана и
  добавить приложение заново через Safari** («Поделиться» → «На экран
  «Домой»») — иначе сохранится старое поведение `black-translucent` и
  проверка ничего не покажет.
- Финальное визуальное подтверждение (полоса исчезла, `.topbar` не наезжает
  на статус-бар) — за пользователем на реальном iPhone после переустановки
  иконки.
