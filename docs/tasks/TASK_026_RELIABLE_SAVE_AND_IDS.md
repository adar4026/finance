# TASK_026 — Надёжное сохранение данных и безопасная генерация ID

**Статус:** `DONE`
**Создана:** 2026-07-29
**Тип:** исправление дефектов (Critical + Medium), защита данных
**Источник:** [`TASK_025_ARCHITECTURE_AND_FINANCIAL_AUDIT`](TASK_025_ARCHITECTURE_AND_FINANCIAL_AUDIT.md) —
C-1 (Critical), M-8, M-10; Фаза 1 плана исправлений (§12).

---

## 1. Исходная проблема

Приложение могло показать пользователю успешное сохранение операции, хотя
физической записи в `localStorage` не произошло.

`AF.Store.save()` честно возвращал `Result`, но локальная обёртка `save()`
(`index.html:2721`) этот результат **выбрасывала**:

```js
function save(){ AF.Store.save(state); renderHeader(); }
```

Ни один из вызывающих участков не мог узнать, состоялась запись или нет.
При переполнении хранилища пользователь видел обычный тост «Расход добавлен ✓»,
операция присутствовала в памяти и во **всех** финансовых итогах (капитал,
аналитика, бюджеты), а после перезагрузки исчезала. Сценарий не гипотетический:
фотографии чеков хранятся data-URL'ами в той же записи `finance_app`, а лимит
`localStorage` — 5–10 МБ; отказ одного `setItem` означает потерю **всех**
накопленных изменений состояния, а не только последнего.

## 2. Root cause

Три независимые причины, каждая устранена отдельно.

1. **Потеря результата на границе слоёв.** Repository (`AF.Store.save`) уже
   работал по правилу Part 4 «ни одной тихой ошибки» и возвращал `Result`,
   но единственная UI-обёртка над ним результат не возвращала и не проверяла.
   Контракт обрывался ровно в одной строке — и дальше вся система вызовов
   (≈50 участков) физически не имела возможности отличить успех от отказа.
2. **Отсутствие семантики отката.** Все CRUD-пути устроены одинаково: сначала
   мутируют `state` в памяти, потом вызывают `save()`. Механизма возврата к
   последнему сохранённому состоянию не существовало, поэтому после отказа
   память и хранилище расходились, а несохранённая запись продолжала
   участвовать в расчётах.
3. **Идентификаторы без гарантии уникальности.** Три схемы генерации
   (`Date.now()`, `Date.now()+Math.random()+k`, `'c'+Date.now().toString(36)`),
   совпадение при создании двух сущностей в одну миллисекунду и общий префикс
   `'g'` у целей и групп счетов.

## 3. Карта всех путей сохранения

`AF.Store.save()` вызывается напрямую в 6 местах, обёртка `save()` — в 46.
Полный разбор по категориям:

| Категория | Пути | Как теперь обрабатывается отказ |
|---|---|---|
| Операции | `saveTx()` (доход/расход/перевод, создание и правка), `delTx()` | форма не закрывается, поля сохранены, success-тост и haptic не выполняются, откат |
| Авто-операции | `processAutoPost()` | возвращает 0 созданных, тост не показывается, откат снимает и операции, и `r.lastPosted` |
| Счета | `saveAcc()`, `delAcc()`, `deleteAccount()`, `archiveAccount()`, `archiveFromEditor()`, `commitAccountOrder()`, `toggleAccGroup()`, `seedAccountGroups()` | редактор остаётся открытым, откат; сидирование — `saveBoot()` |
| Группы счетов | `saveGroup()`, `delGroup()` | редактор остаётся открытым, откат |
| Категории | `saveCat()`, `deleteCat()`, `commitCatOrder()`, `ensureCat()` (кнопка «+» в форме), подкатегории (создание/переименование/удаление, две точки входа) | редактор остаётся открытым, откат, перерисовка фактического состояния |
| Бюджеты | `saveBudget()`, `deleteBudget()` | шторка остаётся открытой с введённым лимитом, откат |
| Цели | `saveGoal()`, `deleteGoal()`, `saveContribGoal()` | шторка остаётся открытой, откат |
| Напоминания | `saveReminder()`, `deleteReminder()`, `markReminderDone()` | шторка остаётся открытой, откат |
| Финздоровье | `snapshotHealth()` | успех не заявляется; откат + сообщение |
| Безопасность | `pinComplete()` (установка/снятие кода), `secToggleBio()`, `openLockPicker()`, `secMarkInactive()`, `secUnlocked()` | код/биометрия не считаются изменёнными без записи; отметки времени — лог без отката (fail-secure) |
| Профиль/настройки | смена фото, имя, валюта, тема, «скрывать суммы», курсы валют | успех не заявляется (кроме курсов — там проверка), откат + сообщение |
| Импорт | `importJSON()` (новая), `importCSV()` | прежняя база не разрушается, частично импортированного состояния не остаётся |
| Резервные копии | `doBackupCreate()`, `doBackupRestore()` | восстановление пишет раньше подмены состояния |
| Демо/очистка | `loadDemo()`, кнопка «Очистить всё» | откат к прежним данным |
| Старт приложения | `seedCategories()`, `seedAccountGroups()` | `saveBoot()` — без отката и без модального шума, но с записью в console |

**Найдено по ходу и учтено:** `seedAccountGroups()` вызывается **из**
`renderAccounts()`, а новый `save()` при отказе сам вызывает `render()` —
прямой путь к бесконечной рекурсии. Поэтому стартовые сохранения выделены в
`saveBoot()`, а в `save()` дополнительно стоит флаг `saveRecovering`.

## 4. Выбранный контракт Result

Второй формат не заводился: используется существующий `AF.Result`
(`js/core/result.js`), а типизация уехала в объект ошибки.

```js
AF.Store.save(state)
  → { ok:true, value:true }
  → { ok:false, error:{ code, message, cause } }

code ∈ 'QUOTA_EXCEEDED' | 'SERIALIZATION_FAILED' | 'STORAGE_FAILED'
```

`message` — готовый пользовательский текст (без имени исключения, стека и
конкретных цифр лимита, которые зависят от браузера и устройства). `cause` —
исходное исключение, только для console.

Локальная обёртка `save()` возвращает **тот же** Result, поэтому любой
вызывающий код пишет `if(!save().ok)return;` и не продолжает успешный
сценарий.

## 5. Механизм отката (атомарность)

Выбран минимальный централизованный вариант без рефакторинга приложения.

- `AF.Store` держит `lastGoodJson` — сериализованное **последнее успешно
  сохранённое** состояние. Строка не создаётся дополнительно: она уже строится
  внутри `save()`, теперь просто не выбрасывается. Точка отсчёта ставится в
  `load()` (`markSaved`), дальше её двигает только успешный `save()`.
- `AF.Store.rollback(state)` восстанавливает состояние **внутрь того же
  объекта** (`delete` всех ключей + `Object.assign`), а не подменяет ссылку:
  на `state` держат ссылки замыкания обработчиков, подмена оставила бы часть
  приложения на несохранённых данных.
- Обёртка `save()` при отказе: откат → перерисовка (`renderHeader()`+`render()`,
  под флагом от рекурсии) → сообщение об ошибке → возврат Result.

Следствия, проверенные тестами и в браузере: после отказа память равна
последнему сохранённому состоянию; несохранённая операция не участвует в
капитале, аналитике и бюджетах; неуспешная правка возвращает прежнюю версию
целиком (без частично изменённого объекта); неуспешное удаление возвращает
запись; повтор не создаёт дубликат.

Для импорта и восстановления копии применён более сильный вариант — «сначала
записать, потом принять»: кандидат собирается **отдельно** от `state`
(`Object.assign({},state,d)`), и `state` подменяется только после успешного
`AF.Store.save(next)`. Прежняя база при отказе остаётся в хранилище нетронутой.

## 6. Обработка переполнения хранилища

`isQuotaError()` распознаёт браузерные варианты: `QuotaExceededError`
(Chrome/Safari), `NS_ERROR_DOM_QUOTA_REACHED` (Firefox), legacy-коды `22` и
`1014`. Отдельно различаются исключение в `JSON.stringify`
(`SERIALIZATION_FAILED`, проверено циклической ссылкой и бросающим геттером) и
недоступное хранилище — private mode, запрещённые cookies (`STORAGE_FAILED`).

Текст для пользователя:

> Не удалось сохранить данные: хранилище приложения заполнено.
> Удалите ненужные фотографии чеков или создайте резервную копию.

Конкретная цифра лимита намеренно не называется. Проверено **настоящим**
переполнением в браузере (без подмены API): хранилище забито балластом до
реального `QuotaExceededError`, затем к расходу приложен data-URL «чека» ~2 МБ —
`isQuotaError()` распознал исходное браузерное исключение, сообщение показано,
форма и прикреплённое фото сохранены, база не изменилась.

Границы соблюдены: на IndexedDB не переходили, формат фотографий не меняли,
новой подсистемы хранения не создавали, ничего автоматически не удаляли.
Вынос фотографий чеков из основной записи оформлен отдельной задачей
`TASK_037` (добавлена в ROADMAP; номера `TASK_027`…`TASK_036` уже заняты
планом TASK_025 §12).

## 7. Новый механизм ID

Новый файл `js/core/ids.js` (`AF.Ids`):

- `newId(prefix)` = время (сортируемость) + счётчик процесса (снимает
  коллизию **внутри одной миллисекунды**) + случайный хвост;
- `uuid()` — `crypto.randomUUID()` при наличии, иначе собственный UUID v4
  (важно: `randomUUID` есть только в защищённом контексте и не во всех версиях
  Safari — без fallback создание любой сущности падало бы с `TypeError`);
- `unique(prefix, taken)` — гарантия отсутствия коллизии **внутри коллекции**;
  принимает массив сущностей, массив id, `Set`, словарь или предикат;
- `forTx/forAccount/forAccountGroup/forCategory/forSubcategory/forGoal/forReminder`
  — обёртки над соответствующими коллекциями `state`.

Префиксы разведены по типам: `t`, `a`, `ag`, `c`, `s`, `gl`, `r` — раньше цель
и группа счетов обе начинались с `g`.

Переведены на генератор: операции (форма, авто-проводка, импорт CSV,
демо-данные), счета (форма и `ensureAcc` импорта), группы счетов, категории
(форма и `ensureCat` импорта), подкатегории (три точки входа), цели,
напоминания (форма операции и редактор).

**Повторная попытка не плодит id.** Идентификатор новой операции выдаётся один
раз на открытие формы (`aTxId` + `newTxId()`), поэтому повтор после ошибки
хранилища переиспользует его.

**Двойное нажатие.** Здесь при проверке в браузере нашёлся собственный дефект
первой редакции правки: `closeSheet()` уходит через `history.back()`, а это
**асинхронно** — второй клик двойного нажатия успевал прийти на ещё видимую
страницу и создавал дубликат с тем же id. Добавлена защёлка `txCommitted`
(снимается только в `openSheet()`), плюс `txSaving` от повторного входа.
Воспроизведено и перепроверено кликами в браузере: три подряд клика по
«Сохранить» дают ровно одну операцию.

**Существующие id пользователя не переписываются**: массовая миграция вне
границ TASK_026, поэтому нестрогие сравнения (`t.id != editId`) сохранены —
они одинаково корректно работают со старыми числовыми и новыми строковыми id.
Дедупликация выполняется только на пути импорта (`dedupeIds()`), где чужой
файл мог принести повторяющиеся id и незаметно затереть сущность.

## 8. Импорт и резервные копии

- Импорт JSON вынесен в `importJSON()`: кандидат собирается отдельно, внутри
  каждой коллекции повторяющиеся и пустые id перевыдаются (`dedupeIds`, с
  отчётом в тосте и console), запись выполняется до подмены состояния.
- `doBackupRestore()` больше не делает `state=res.value` до записи.
- Импорт CSV: id операций проверяются и против существующих операций, и внутри
  самой пачки (`usedTxIds`); при отказе записи откат убирает и добавленные
  операции, и созданные по пути категории/счета.
- Глубокая нормализация импорта (валидация схемы, предпросмотр, выбор
  «заменить/добавить», отчёт «было N — стало M») намеренно оставлена
  `TASK_034`.

## 9. M-10 — `Math.min(...массив)`

Добавлены итеративные `minOf()`/`maxOf()`; spread убран с четырёх мест, где
массив не ограничен по размеру (`renderCapChart`, `catTxRange`, `statsRange`,
`buildStatsOverview`). Семантика воспроизведена **в точности**, включая
NaN-поведение: исправление H-6 относится к `TASK_027` и здесь намеренно не
делается, чтобы не смешивать задачи. Малые фиксированные массивы (12 месяцев,
30 дней, 7 дней недели) оставлены как есть.

## 10. UX при ошибке

Редизайна нет. Использован **существующий** механизм тостов, добавлен заметный
вариант `.toast.err`: белый текст на `#d92d20` (одинаково читаем в светлой и
тёмной темах), многострочный, ограниченной ширины, с отступом снизу через
`env(safe-area-inset-bottom)` (не перекрывает системные кнопки), **не исчезает
сам** — закрывается касанием. Обычный `toast()` снимает класс `err`, поэтому
success не наследует красный вид. Технические подробности (код ошибки) идут
только в console, без пользовательских данных.

## 14. Известные ограничения

1. Откат восстанавливает **всё** состояние целиком, а не отдельную сущность:
   если между двумя сохранениями были изменены другие части `state`, они тоже
   вернутся к последнему сохранённому виду. Для текущей архитектуры (каждая
   мутация сразу сопровождается `save()`) это корректно и является самым
   дешёвым надёжным вариантом; более тонкая гранулярность потребовала бы
   полного рефакторинга слоя данных.
2. Хранится дополнительная копия состояния в виде строки. Дополнительной
   сериализации это не добавляет (строка и так строилась в `save()`), но
   удваивает объём памяти под данные — заметно только при больших фото чеков.
   Это ещё один аргумент за `TASK_037`.
3. Стартовые сохранения (`seedCategories`, `seedAccountGroups`) не
   откатываются и не показывают модального сообщения — только запись в
   console. Пользовательского действия за ними нет, а откат в момент
   `render()` вызвал бы рекурсию.
4. Отметки времени безопасности (`lastActiveAt`) при отказе записи не
   откатываются — их отсутствие трактуется `shouldLock()` как fail-secure.
5. Существующие id пользователя не мигрировали; сравнения остались
   нестрогими. Дедупликация выполняется только на пути импорта.
6. `NaN`-поведение `minOf`/`maxOf` сохранено намеренно (H-6 → `TASK_027`).
7. Реальная проверка на iPhone Safari/PWA в этой сессии не выполнялась
   (открытый пункт, общий с `TASK_015`/`TASK_017`/`TASK_023`).
