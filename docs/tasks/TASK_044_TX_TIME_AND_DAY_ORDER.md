# TASK_044 — Время операции и порядок внутри дня на Главной

**Статус:** DONE (commit + push в `main` — по требованию постановки)

## Контекст

На Главной (`#recentList`) и на остальных списках, сгруппированных по дням
(«Все операции», операции счёта, операции категории, результаты поиска),
операции внутри одного дня показываются в обратном порядке: новые — внизу.

Причина найдена в коде: внутри дня сортировка выполняется как
`items.sort((a,b)=>b.id-a.id)` (четыре места в `index.html`: `renderRecent`,
`homeGroupedTxHtml`, `groupedTxHtml`, `catxGroupedTxHtml`). До `TASK_026`
id операции был числом (`Date.now()`), и вычитание давало порядок «новые
сверху». С `TASK_026` id — строка (`t<base36-время>-<счётчик>-<hex>`),
`b.id-a.id` → `NaN` → компаратор возвращает «равно» → `Array.prototype.sort`
(стабильный) оставляет порядок вставки: старые сверху, новые внизу.

Точного времени у операции в модели нет: `tx.date` — `'YYYY-MM-DD'`.

## Цель

1. У операции появляется точное время (`ЧЧ:ММ`): новая операция получает
   текущее локальное время устройства, пользователь может изменить его в
   форме.
2. Внутри дня операции сортируются по времени по убыванию (19:30 выше 16:45
   выше 10:00); дни — по-прежнему от новых к старым.
3. Старые операции без времени продолжают корректно отображаться, время им
   не подставляется, дата не меняется; их взаимный порядок — стабильный
   резервный (порядок создания по id, новые сверху), не «прыгает» после
   перезагрузки.
4. Время ненавязчиво показывается в карточке операции.

## Модель данных

- Новое необязательное поле операции **`time`** — строка `'HH:MM'` (24 ч,
  локальное время устройства, без секунд и таймзоны). Отдельное поле, а не
  `occurredAt`: `date` остаётся `'YYYY-MM-DD'` и не затрагивается (экспорт,
  импорт, аналитика, периоды, календарь читают `date` как раньше).
- Принцип «пусто = ключа нет» (как у `payee/tags/location`, `TASK_015`):
  невалидное/пустое значение → ключ удаляется. `SCHEMA_VERSION` не
  поднимается — ключ необязательный, нормализация идемпотентна (тот же
  приём, что `importBatches`/`settings.security`).
- Нормализация — в `AF.Store.migrate` через новый сервис (с проверкой наличия
  сервиса, инвариант совместимости `TASK_015 §0`).

## Требования

1. Форма: строка «Время» (`<input type="time" id="fTime" class="tx-native">`
   поверх строки, как `#fDate`), видимое значение `ЧЧ:ММ`; для новой
   операции — текущее локальное время; при редактировании — сохранённое
   время либо «—» (старая запись; поле пустое, время не подставляется).
2. Сохранение: `time` пишется только если поле заполнено и валидно; пустое →
   ключ удаляется (в т.ч. при редактировании старой записи без изменения
   времени).
3. Сортировка внутри дня (`AF.Services.TxTime.compareInDay`):
   1) по времени по убыванию; 2) запись со временем выше записи без времени;
   3) без времени — по метке создания из id по убыванию (число `Date.now()`
   старых id либо base36-время из `t…` id `TASK_026`); 4) иначе — по позиции
   в массиве (позже добавленная выше). Полностью детерминированно.
4. Дни — по-прежнему `date` по убыванию.
5. Отображение: время первым элементом подзаголовка (`home-sub` / `.t2`),
   `tabular-nums`; при отсутствии времени подзаголовок не меняется.
6. Все четыре сгруппированных списка используют сервис; `b.id-a.id` в
   `index.html` не остаётся.

### Что реализовано

- **Причина бага** подтверждена и устранена: `b.id-a.id` (4 места) → `NaN`
  для строковых id `TASK_026` → стабильный `sort` оставлял порядок вставки.
  В `index.html` компаратора `b.id-a.id` больше нет (проверяется тестом).
- **Сервис** `js/services/tx_time_service.js` (`AF.Services.TxTime`,
  подключён ДО `store.js`): `normalize`, `minutes`, `localDate`,
  `localTime`, `normalizeTx`, `idStamp`, `compareInDay`, `compare`,
  `sortDay`, `sortAll`. Порядок внутри дня: время по убыванию → запись со
  временем выше записи без → метка создания из id по убыванию (числовой
  `Date.now()` или base36 из `t…-`) → позиция в массиве (позже добавленная
  выше). Полностью детерминированно, не зависит от стабильности `sort`.
- **`AF.Store.migrate`** — вызов `TxTime.normalizeTx` для всех операций с
  проверкой наличия сервиса (инвариант `TASK_015 §0`).
- **Форма**: строка «Время» (`#timeRow`, `#timeRowVal`, `<input type="time"
  id="fTime" class="tx-native">`) после «Дата». Новая операция — `localDate`/
  `localTime` из одного момента (раньше `#fDate` брала UTC-дату через
  `toISOString`); редактирование — сохранённое время либо пустое поле и «—».
  `syncTimeRow` в `syncTxRows`, `onchange` → haptic + перерисовка.
- **`saveTx`**: `time = TxTime.normalize(#fTime)`; `applyTxTime(t,time)` во
  всех четырёх ветках (перевод/расход-доход × новая/редактирование) — пусто →
  `delete t.time`. Fallback даты — локальная.
- **Сортировка**: `renderRecent` → `TxTime.sortAll(list)`; `homeGroupedTxHtml`,
  `groupedTxHtml`, `catxGroupedTxHtml` → `TxTime.sortDay(byDay[day])`. Порядок
  дней (`b.localeCompare(a)`) не менялся.
- **Отображение**: `txTimeHtml(t)` → `<span class="tx-time">19:30</span> · `
  первым элементом подзаголовка в `homeTxRow` (Главная, категория) и `txRow`
  («Все операции», счёт, поиск), для расхода/дохода и перевода. Без времени
  подзаголовок как раньше. CSS: `.tx-time{font-variant-numeric:tabular-nums}`.
- **`sw.js`**: `tx_time_service.js` в precache, `finance-v175` →
